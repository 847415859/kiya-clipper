# 发布账号网页登录

更新日期：2026-11-18。

## 使用方法

1. 在网站顶部选择要管理的主播，然后打开 **设置 → B站发布账号**。
2. 选择扫码、账号密码、短信、浏览器或 Cookie 登录，按下面说明完成登录。
3. 网站显示登录账号的昵称和 UID。核对后点击 **确认用于发布**，才会替换当前主播的发布账号。
4. 可点击“检查登录状态”验证凭证；如切片号统计也使用这个账号，点击“同步为切片号统计账号”，再到精排记忆更新数据。
5. 手机打开设置页面时，可长按保存二维码，再使用 B站扫一扫的相册识别功能。

任何方式登录成功但未在网站确认时，原发布账号保持不变。请求过期后重新开始；验证暂时失败时会提示并重试，不会立即覆盖现有凭证。

## 五种登录方式

| 方式 | 操作与要求 |
| --- | --- |
| 扫码登录 | 使用 B站 App 扫描二维码并确认。手机打开后台时可保存二维码，通过相册识别。 |
| 账号密码 | 填写 B站账号与密码，密码使用 B站提供的公钥加密后提交。若出现人机验证，手动完成后继续。 |
| 短信登录 | 填国家代码（中国大陆默认 86）和已注册手机号，发送短信；需要时先手动验证。填写短信验证码并登录。发送成功后 60 秒才能重发，单个请求最多尝试 5 次验证码。 |
| 浏览器登录 | 获取授权链接，点击打开 B站官方页面，在官方页面完成登录与授权，再回到后台等待查询结果。与 biliup 的浏览器登录一致，不安装插件或读取本机浏览器数据库。 |
| Cookie 登录 | 支持 Cookie 请求头、浏览器导出的 Cookie JSON 和完整 biliup 登录 JSON，也可选择本地 JSON/TXT 文件，最大 64KB。普通 Cookie 至少包含 SESSDATA、bili_jct；先验证账号，再通过官方授权流程换取投稿所需的完整凭证，并再次核对 UID 一致性。 |

网站远程访问必须使用 HTTPS 才能输入密码、发送短信或导入 Cookie；本机 localhost 开发环境可使用 HTTP。网站会清空已提交的 Cookie 和验证码；密码仅在当前页面等待人工验证期间暂存，结束、取消或离开设置页面即清空，不写入浏览器持久存储或服务器凭证文件。

B站可能要求人机验证、额外身份核验或拒绝某种登录方式。人机验证由用户操作官方 GeeTest 组件；组件在独立的受限框架内运行，不能读取设置页面中的密码和 Cookie。额外身份核验不等同于登录成功，页面会提示切换到浏览器授权。服务不会自动绕过验证，也不会将官方拒绝结果伪装为成功。

“停用发布账号”仅停用当前主播的网站投稿凭证，不撤回历史作品，也不退出手机 B站账号。停用后不会自动使用旧服务器凭证投稿，需要重新扫码才能恢复。

后台管理员登录、录播姬登录和 B站发布账号相互独立。退出后台网站不会自动停用已经设置好的发布账号。

## 账号作用范围与任务保护

- 网站账号按当前主播隔离，发布和相关查询优先使用该主播的网站凭证。
- 未设置网站账号时，继续兼容现有 `KIYA_BILIUP_COOKIE` 和 `publish.bili.cookie` 等配置。
- 网站明确停用或凭证损坏时，不静默切回另一份旧凭证。
- 更换账号不迁移旧账号的作品；同步统计 UID 也不改变历史投稿绑定。
- 有投稿正在排队或上传时，暂不允许切换或停用账号。账号更新与新投稿任务入队共用互斥保护。
- 异步任务保存服务器确定的主播标识，运行和服务重启恢复时使用提交时的主播上下文，不跟随浏览器之后切换的主播变化。
- 不允许旧二维码确认覆盖另一操作已经设置的新账号；发生冲突时需要重新扫码。

## 服务器存储

网站凭证保存在当前主播输出目录的 `_credentials/bili.json`，格式兼容现有 biliup 投稿命令。输出目录沿用项目的多主播和旧目录兼容规则。

- `bili.json`：当前凭证，或明确停用标记。
- `bili.previous.json`：上一次网站托管凭证的恢复备份；首次启用不会改写原有外部登录文件。
- `pending/<随机编号>.json`：临时扫码请求和待确认凭证；请求有有效期，后续查询或创建请求会清理过期状态。

Linux 上凭证文件权限为 `600`、凭证目录为 `700`；使用原子替换，避免写入中断留下半份文件。目录位于 Git 忽略的输出数据内，不提交到代码仓库。备份输出数据时，这些文件应按账号凭证保护。

登录服务返回二维码图片、官方授权链接、人机验证公开参数、状态、昵称和 UID，不返回 Cookie、access token 或 refresh token。密码、验证码和导入内容通过进程标准输入传入 worker，不放入命令参数或环境变量，不进入普通任务日志；异常不输出上游响应、请求头或凭证内容。请求仅能由创建它的后台会话、在对应主播下继续、查询和确认；更改状态的接口沿用现有登录与 CSRF 保护，响应禁止缓存。

## 部署

更新前端、后端和 worker，并在服务器的 worker 虚拟环境安装新增依赖：

```bash
cd /opt/kiya-clipper/worker
.venv/bin/python -m pip install -r requirements.txt
```

重新构建并部署后台后重启 `kiya-admin`。新增依赖包括 `qrcode[pil]` 和密码加密使用的 `cryptography`。网页登录不代替安装 biliup，服务器仍需有可执行的 biliup 才能实际投稿。服务器需能访问 B站登录接口和账号查询接口；客户端需能加载 GeeTest 官方验证资源。反向代理需将 `/publish-captcha` 与 `/api/` 一起交给后台，不要给验证码页面额外叠加 `X-Frame-Options: DENY` 或全站 `frame-ancestors 'none'`。其他页面保留原限制。网络或风控失败会显示无法验证，不将其直接判断为登录过期。

首次上线后，需要用户在设置页面自行扫码并确认；开发测试不使用真实用户账号或触发真实投稿。

## 实现与验证

- 网站入口：`admin/src/components/PublishAccount.vue`，由设置页面加载。
- HTTP 服务：`PublishAccountController`、`PublishAccountService`。
- 登录 worker：`worker/scripts/publish_account.py`、`worker/clipper/publish_account.py`、`worker/clipper/publish_login_methods.py`。
- 投稿、精排记忆查询和指标采集共同识别网站托管凭证；未托管时保持旧配置兼容。
- 扫码使用与 biliup 对应的 TV 登录流程，保留 token 和 Cookie 的兼容格式。协议及字段参考 [biliup 登录实现](https://github.com/biliup/biliup/blob/master/crates/biliup/src/uploader/credential.rs)。
- 自动测试覆盖扫码、过期、网络失败、RSA 密码加密、短信人工验证续接及次数限制、Cookie 转换和 UID 一致性、浏览器授权、显式启用、账号冲突、停用后不回退、会话及主播隔离、投稿期间禁止切换、标准输入传递、敏感字段过滤、验证码页面策略和任务上下文恢复。
- 浏览器联调使用模拟登录服务，不发送真实短信、不使用真实密码或 Cookie。五种方式在 B站当前风控条件下的可用性，以及实际投稿，仍需部署后由账号持有人验证。
