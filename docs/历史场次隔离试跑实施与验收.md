# 历史场次隔离试跑实施与验收

## 边界与操作方式

- 本轮经用户确认允许本地代码写入与测试。Git 仅作查询，没有暂存、提交、回滚或推送；没有远程部署或投稿。
- 「场次」操作区提供唯一写入口「隔离试跑」；「新场验收 → 隔离验收队列」继续只读。
- 当前交付启用明确的 fixture 模型模式：真实文件、HTTP、Worker、FFmpeg/Remotion 渲染，模型决策为模拟。付费/live 成本未知时前置停止，没有为实际付费运行编造预算估算或调用模型。
- 部署后的真实历史录像 + 实际模型运行仍需独立验收；本轮不将模拟审片当作实际语义质量结论。

## 链路与目录

1. 场次页 GET options，由服务器解析候选、场次及主播归属、素材可读性、路径和符号链接；展示候选、缺段、步骤、零费用上限。
2. 管理员确认后 POST 仅携带 `rank/confirmation/rerunTaskId`。不接收客户端文件路径、任意命令、模型配置或发布开关。
3. 队列任务具有 `source=historical_trial` 与独立 `history-UUID`，不依赖下播事件；原始文件哈希绑定输入。并发提交使用进程内互斥与操作系统文件锁；活跃任务返回原 ID，明确重跑保留新旧记录。
4. 独立 Worker 领取任务，将选中候选及必要素材复制到该任务目录，复用 Production/检查点/版本/质检/库存结构。可恢复的检查点复用；失败或预算停止落盘原因。
   - fixture 完成可播放媒体显示为「模拟试跑预览（非正式合格库存）」，`previewPlayable/versions.playable` 独立于正式库存 `playable`；模拟产物不计入正式合格成片数量。
5. 只读验收页按任务 ID 查看状态与媒体；复用版本/审片/质检/媒体哈希校验和 Range 播放。

默认隔离根为 `/var/lib/kiya-next-session-acceptance/history`：

- `queue/<taskId>.json`：不可变提交记录。
- `status/<taskId>.json`：领取和执行结果。
- `locks/`：提交幂等锁及 Worker 领取锁。
- `production/<taskId>/input/`：快照及拷贝素材。
- `production/<taskId>/<rank>/`：版本、报告、审片和隔离库存。
- 模拟用量与实际费用明确区分，当前实际请求与费用均为零，不接触生产账号用量和生产账本。

## 本地复现

在仓库根执行；Windows 使用现有 Python3.12 虚拟环境与 JDK17。不要使用系统 Python3.8。

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONIOENCODING='utf-8'
$env:JAVA_HOME='D:\Develop\Java\JDK\jdk-17.0.14+7'
$env:PATH="$env:JAVA_HOME\bin;$env:PATH"
$env:REMOTION_CONCURRENCY='4'
npm --prefix admin run build
$env:PYTHONPATH='worker'
mvn -f backend/pom.xml test
mvn -f backend/pom.xml test-compile dependency:build-classpath -Dmdep.outputFile=target/historical-classpath.txt -Dmdep.includeScope=test
worker/.venv/Scripts/python.exe -m pytest worker/tests/test_historical_trial_worker.py -q
node --test admin/tests/*.test.mjs
worker/.venv/Scripts/python.exe admin/tests/historical-trial-e2e.py
```

HTTP/browser 脚本使用 test-scoped H2 启动临时本地 Spring 服务（随机端口），通过真实 CSRF 与登录提交任务，调用实际 Worker，再通过真实媒体端点验证 Range、播放及拖动。每次夹具使用新目录，旧证据保留；脚本 finally 结束临时服务器。测试启动器仅在 test classpath，不进入正式 JAR。

## 部署与回滚（仅说明，未执行）

### 部署前

- 备份当前 JAR、Worker/renderer 程序包和隔离根；数据库现有身份认证复用，无新增业务表。
- 确认管理员身份具备 ADMIN 角色，CSRF 保持开启；确认服务器 `REC_DIR`、仓库路径、`KIYA_ACCEPTANCE_DIR` 与 Worker unit 完全一致。
- 确认磁盘空间：Worker 对候选涉及的录播段执行完整复制，不是硬链接，也不是只复制几秒；大历史段可能占用较多空间和哈希时间。
- 安装依赖：Java17、Node/Remotion、FFmpeg/ffprobe、Worker Python 依赖、Chromium 与字体。渲染依赖按原制作流程预构建。
- unit 将仓库挂载为只读，必须预构建 `renderer/build`，并确保其比 renderer/src 更新；通过 unit drop-in 设置 `REMOTION_BROWSER` 指向已安装浏览器的实际路径，避免首次运行向只读仓库安装浏览器或写构建缓存。升级 renderer 源码后应在发布阶段重新构建，而非由隔离 Worker 运行时写程序目录。

### 启动与权限

- 后端默认 `kiya.historical-trial-fixture-enabled=false`。启用本轮零费模式需显式设置 `KIYA_HISTORICAL_TRIAL_FIXTURE_ENABLED=true`，不启用付费模型。
- Worker 必须显式传 `--fixture`，否则任务进入预算/配置暂停，不调用模型。
- 后端账号需要读取原候选和录像，写入 `history/queue,status,locks`；Worker 读取源素材，写入隔离根与必要渲染缓存。二者均不应获得生产队列写权限。
- 部署参考 unit 位于 `deploy/admin/kiya-historical-trial-worker.service`。应用前逐项核对 User/Group、路径与只读/可写挂载，特别是自定义录播位置及 Remotion 缓存。
- 后台root、Worker kiya的共享组、原子JSON权限与旧目录迁移，按 [Linux双用户权限说明](<历史隔离试跑Linux双用户权限.md>)；仅修复history树，不对acceptance或生产目录递归改权限。

```bash
# acceptance父目录需已存在且kiya可遍历；仅初始化或迁移history。
sudo python3 deploy/admin/prepare-historical-trial.py --root /var/lib/kiya-next-session-acceptance/history --user kiya --group kiya
sudo install -m 0644 deploy/admin/kiya-historical-trial-worker.service /etc/systemd/system/kiya-historical-trial-worker.service
sudo systemctl daemon-reload
sudo systemctl enable --now kiya-historical-trial-worker
sudo systemctl restart kiya-admin
sudo systemctl status kiya-historical-trial-worker --no-pager
```

启用后，管理员日常通过网页提交和查看，无须手动执行 Worker 命令。不要同时把历史任务目录接入生产消费器；不要给此服务启用投稿服务或账号 Cookie。

### 回滚

1. 关闭后端 fixture 提交开关，停止接受新任务；停止历史试跑 Worker。勿先删锁文件或正在处理的状态。
2. 完整保留 `history/` 下任务、状态、快照、账本和媒体证据，再替换备份的旧 JAR 与 Worker/renderer 程序包。
3. 重启原后台。旧页面没有历史入口，生产队列始终保持原位置，历史产物不搬入生产库存。
4. 恢复本版本后，Worker 可以继续验证并复用有效检查点；已结束失败任务通过网页明确重跑创建新 ID，旧记录不覆盖。

```bash
sudo systemctl stop kiya-historical-trial-worker
sudo cp -a /var/lib/kiya-next-session-acceptance/history /var/lib/kiya-next-session-acceptance/history.backup-$(date +%Y%m%d-%H%M%S)
# 使用部署前保存的程序包还原对应路径，再重启后台；不使用 Git 回滚命令。
sudo systemctl restart kiya-admin
```
