# Kiya 新场验收页面实施任务书

## 交付目标

部署后，用户通过 **场次 → 新场验收 → 查看详情** 查看新直播场次的验收结果。页面应回答以下问题。

1. 监控最后一次成功观察到什么状态，有没有记录这场直播的下播事件。
2. 下播事件有没有对应的队列任务，是否能唯一匹配这场录播。
3. Worker 做到了哪一步，有多少候选，当前卡点和依据是什么。
4. 是否有通过质检、审片并入库的成片，能否直接打开并拖动到问题位置。

日常查看在网页完成。操作系统日志可以作为开发排查依据，页面应直接提供使用者需要的结论与证据。验收入口保持只读。访问、刷新和播放均不得触发入队、续跑、付费请求或投稿。

## 当前基线与工作区

- 对话中最后确认的服务器部署提交是 `f317336`。开工先核对当前分支、提交和工作区。工作区可能已有未提交的第一版「新场验收」入口，优先接着完善。若三方使用独立 checkout，先确认能否看到同一份改动。
- 第一版提供独立验收队列的读取、场次列表、详情和成片入口。前端构建及 17 项定向后端测试已在本地通过，服务器是否已部署这一版需要另外核实。
- 页面入口在 `admin/src/views/Sessions.vue`，请求封装在 `admin/src/api.js`。后端复用 `SessionController`、`OperationsQueueService`、`WorkerPaths` 和 `KiyaProperties`。列表与详情应共用同一套状态推导。
- 现有隔离观察任务写入 `/var/lib/kiya-next-session-acceptance`。后台通过 `KIYA_ACCEPTANCE_DIR` 配置验收读取目录，默认与观察任务的目录一致。生产队列继续使用现有 `KIYA_OPS_DIR`。用户无需为查看验收临时改动生产后台指向。
- 服务器上的观察任务可能只运行到入队，队列中已有任务而 Worker 尚未领取属于可展示的正常状态。

## 数据来源与归属

| 事实 | 首选来源 | 展示规则 |
|---|---|---|
| 监控最近一次记录 | 验收目录的 `monitor-state.json` | 单独展示最近轮询时间、最近记录的直播状态和查询失败次数。时间过旧或查询失败时明示。无记录时显示「尚无轮询记录」。 |
| 下播事件 | `operations/ended/<job>.json` | 以房间、主播及录播时间范围核对归属。监控观察到的开播或下播时间明确标为「监控观察时间」。 |
| 已入队 | `operations/queue/<job>.json` | 使用任务 ID 去重显示。下播事件和队列条目分别展示，避免把两份记录数算成两条任务。 |
| 录播对应关系 | 队列记录及后台现有录播匹配 | 显示可核对的房间、场次、分段和稳定性。只能确认部分信息时按已有证据显示。无法唯一匹配时保留待核对状态。 |
| Worker 进度 | `operations/status/<job>.json` | 显示当前步骤、最近更新时间、处理次数、下次可处理时间、选中及暂缓的候选。未领取时明确显示「已入队，等待制作」。 |
| 候选状态与变更 | `operations/production/<job>/summary-selected.json` 或 `summary.json`、候选 `state.json` | 以候选日志和检查点补足场次摘要。保留历史版本与当前版本的关系。 |
| 技术与内容结论 | 与成片匹配的质检报告、证据报告和审片记录 | 按版本及媒体标识关联，避免把返修前的意见显示成当前成片的结论。 |
| 成片与库存 | 当前候选的 `inventory.json` 和媒体文件 | 确认归属队列、场次、候选和当前库存版本后才提供播放入口。 |
| 模型与预算 | Worker 预算快照和可核实的请求审计 | 分辨请求尝试、缓存、已知用量、预留和已结算费用。费用未知时保留未知。 |

开发时以当前代码和实际 JSON 字段为准。已有记录无法回答的问题应明确标为「未记录」或「待核对」。文件更新时间可以作为辅助信息，并标为更新时间；事件发生时间应来自事件或状态记录。新 API 时间优先使用带时区的 ISO 8601，页面统一展示北京时间。旧版不含时区的日志时间须先确认时区才能转换。

## 页面结构

### 直播与队列总览

- 页面入口为「场次 → 新场验收」。默认显示最近一次监控观察、是否有下播记录、场次、任务状态、当前步骤和成片数。
- 明确区分「等待监控记录」「已观察到直播，等待下播」「已记录下播，暂未入队」「已入队，等待制作」。
- 未匹配的任务也要可见。展示任务标识和可公开的匹配原因，便于判断缺录播、时间范围冲突或识别到多个场次。
- 如果只看见一个任务条目，提示「观察到 1 条任务」。只有重复触发验证通过后，验收报告才能写「下播去重已验收」。
- 保留手动刷新。若增加自动刷新，仅在面板打开且页面可见时运行，关闭后停止。网络刷新失败时保留上次成功结果，并显示状态可能已过期。

### 场次详情与制作时间线

- 按实际记录展示录播核对、转写、粗筛、精排、候选制作、补证、草稿、渲染、审片与入库。折叠默认只显示当前阶段和需要关注的步骤。
- 展示已有的开始、更新时间、重试次数及下次可处理时间。等待录播、预算或磁盘空间时，显示具体原因。步骤历史有依据才展示。
- 明确区分「已处理，无合格候选」「候选待复核」「技术质检失败」「已有合格成片」。`prepared` 单独出现时只能说明队列处理完成，成片状态以有效库存和媒体为准。

### 候选、返修和成片

- 首屏展示候选编号、当前版本、主要卡点和简明结论。展开显示模型原始理由、补证区间、返修动作、质检项目、内容审片和证据覆盖。
- 各区间标注「整场原片秒数」或「成片秒数」。已有映射时同时展示两者，并支持从成片位置回看。
- 模型建议返修但缺少动作或成片区间时，保留审片原始理由，提示缺失字段，状态显示待人工复核。
- 返修后默认展示当前文件对应的报告。历史审片和旧成片保留在对应版本下，避免用旧结论覆盖新结果。
- 合格成片显示 720p 等实测规格、时长、音频连续性、必保证据覆盖和实际视频审片结论。复用现有鉴权和媒体入口，检查网页可播放、可拖动。技术质检通过和内容审片通过分别显示。
- 示例包括候选 #5。开头花字在返修版已移除，中段推镜位于成片 10.11–12.11 秒。旧版媒体总时长接近一致，但可解码音频采样在 37.035–38.528 秒存在断点。修复后通过连续性检查。这类细节由对应报告和版本决定，页面不要写死这一场的编号或数值。

### 预算和用量

- 展示可核实的北京时间账本日期、剩余额度、预留、已知结算、未知费用和等待预算原因。
- 区分实际 HTTP 尝试次数、缓存命中和模型返回的 token 用量。数据未落盘时显示未知，避免把未知写成零调用或零费用。
- 页面只读取账本。刷新页面不会消耗预算。

## 技术边界

- 生产与隔离验收队列使用独立根目录。相同场次号出现在两边时，列表、详情和媒体请求仍走对应队列。验收入口不暴露补入、续跑、稿件发布或其他写操作。
- 沿用现有后台登录鉴权。客户端只传场次和候选标识。服务端验证媒体归属和库存版本，限制实际文件路径在对应队列目录内，并沿用视频 Range 响应。
- 错误信息返回面向用户的阶段、原因、错误码和区间。原始日志、Cookie、API Key、完整环境配置及任意服务器绝对文件路径不应发送给浏览器。检查现有错误和模型理由里的内嵌路径等内容。
- 兼容旧队列和部分落盘的记录。状态文件缺失、媒体失效或目录不可读时有明确提示，页面不崩溃，其他正常场次仍可显示。
- 范围限定在验收展示、数据聚合、播放和相关测试。候选 #5 的专用脚本、花字 ID 和媒体哈希只作为测试或历史参考。保留当前用户修改与已入库产物。

## 验收矩阵

| 场景 | 必须看到的结果 |
|---|---|
| 无监控记录、直播中、监控查询失败 | 三种情况可区分，显示实际最近记录时间，刷新失败保留上一次数据。 |
| 只有下播事件、事件已入队、队列无法唯一匹配 | 三种情况可区分。同一事件与队列条目只显示一项；匹配不确定给出明确说明。 |
| 等待录播、等待预算、Worker 暂停 | 显示当前步骤和已记录的原因，能看到已有下次处理时间。 |
| 处理完成无成片 | 显示「处理完成，无成片」，带候选处置结果。 |
| 音频断点或审片缺字段 | 展示成片秒数、质检错误或审片原始理由。审片意见未定位时进入待复核。 |
| 返修后入库 | 页面可直接打开当前版本 MP4。请求鉴权和拖动播放正常，旧审片仍能对应旧版本。 |
| 同名生产场次与验收场次 | 各自展示正确结果和媒体。验收详情没有生产恢复操作，媒体接口无法跨目录读取。 |
| 页面打开和刷新 | 模拟前后对比队列、账本和成片文件，验证没有写入或付费请求。 |

## 实施顺序与交付

1. 核对当前分支、已有验收页面及现场 JSON 结构，确认能够复用的入口和状态字段。
2. 补齐后端只读数据聚合、时间和错误字段处理，先用模拟记录验证生产与隔离读写边界。
3. 完成页面总览、可展开详情和视频播放。页面优先显示当前情况，历史和原始审片理由按需展开。
4. 运行前端构建、后端相关测试和浏览器验收。保留正常流程、缺录播、预算暂停、质检失败和入库播放的截图及复现命令。
5. 提供对应提交、变更文件、部署步骤和回滚方式。已部署的页面和服务器上真实下播、真实产出成片的结果分别报告。没有线上能力时交付可复现步骤和当前阻塞点。

最终交付以用户能在网页查看 **有没有下播任务、做到了哪一步、卡在哪里和是否有成片** 为准。
