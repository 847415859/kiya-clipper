# VTuber 直播切片技术方案

Nov 9, 2026 · @qiankun

## 方案概要

系统在 VTuber 直播结束后 1 小时内，自动产出 5–10 条带花字、表情包、音效和运镜的竖屏有趣切片，经人工审核后发布到自己的切片号，为主播引流。核心思路是三段式：**便宜信号粗筛 → 多模态大模型精排并写剪辑脚本 → 模板化渲染**。

| 项 | 第一版（MVP） | 后续扩展 |
| --- | --- | --- |
| 平台 | B站直播 | 仅 B站，暂不扩展其他平台 |
| 主播 | 首位：娜由纪雅kiya（B站 UID 646830928，直播间号由 UID 自动查询） | 10 位以上，按品类配置 |
| 片段类型 | 破防尖叫、口胡、互动名场面、杂谈金句 | 游戏高能操作、多人联动 |
| 包装 | 推镜、震屏、花字、贴纸、音效、字幕、片尾引流卡 | 定格、脑补配图、弹幕飘屏、片头钩子、流行梗与二创 |
| 输出 | 1080×1920 成片 + 标题封面 | 剪映草稿（剪辑师加入后）、横屏合集、多平台自动发布 |
| 发布 | 人工审核后手动发布到自己的切片号 | 审核后一键发布 |

**成功标准**：审核通过率 ≥ 60%；每条切片人工处理 ≤ 5 分钟；切片带来的主播关注增长可追踪。这些数字是建议的起始目标，跑完前 10 场后再校准。

## 当前实现与原方案的差异（2026-11-10）

本页第一版是目标设计。实际按“预算最小、先跑通”落地，下表是现在真实的样子；后面各章保留原设计，作为目标架构和升级路径，标题带“（目标设计）”的章节表示还没有照此实现。**维护约定：以后每次功能优化，先改本节和对应章节，再算完成。**

| 方面 | 原方案 | 当前实现 |
| --- | --- | --- |
| 服务器 | 常驻 4 核 8G，GPU 按场次按量租用 | 一台阿里云 ECS 2 核 2G（Ubuntu 24.04）跑录制、粗筛、后台和渲染，没有 GPU；重活用 nice 低优先级，录制优先 |
| 录制 | 录播姬或 blrec + Python 弹幕采集器 | 录播姬命令行版（systemd 服务 brec），每 30 分钟一段，存 flv + xml 弹幕，不用 Docker |
| 任务编排 | Redis Stream + Python Worker 回调，失败重试 3 次 | 没有 Redis。下播后由 cron 监控脚本（每 3 分钟一次）依次调用 worker 脚本：转写（开了才做）→ 粗筛 → 更新精排记忆 → 精排 → 剪切；后台手动操作走 Spring Boot 里的单线程任务队列（job 表） |
| 数据存储 | 16 张 MySQL 表 | MySQL 只有 6 张表（sys\_user、live\_session、candidate、subtitle\_style、job、app\_config），启动时执行 schema.sql，没有 Flyway；其余都是每场 output/<场次>/ 下的 JSON（candidates、rerank、transcript、review\_meta、edits、publish 等）和全局的 memory.json、memory\_decisions.json |
| 粗筛 | 弹幕 + 音频 + 镜头切换 | 弹幕密度、情绪词、礼物、音频响度、画面变化、尖叫、笑声（有转写才有），弹幕延迟自动估计；低于分数线 min\_score 的不出候选，不凑数 |
| 转写 | FunASR / faster-whisper 跑在 GPU 上 | 百炼 fun-asr 录音文件识别接口 + 热词表，约 ¥2 一场，不需要 GPU |
| 音频事件和画面检测 | 笑声 / 尖叫模型、动漫人脸检测、PySceneDetect、超分 | 信号处理实现（高频占比判尖叫，音高稳定判唱歌 / 音乐），笑声来自转写文本；人脸检测、PySceneDetect、超分都没接 |
| 精排 | 多模态大模型 + 纯文本模型 | 百炼 qwen3-vl-plus：每个候选 8 张截图 + 原话 + 弹幕 + 精排记忆，pydantic 校验、请求缓存，起止点对齐句子；命中禁区话题的判不切 |
| 剪辑脚本 | 每条 2–3 个版本（纯享、综艺、整活） | 目前只生成综艺版 AI 初稿（花字、放大运镜、贴图，密度约束强制执行），人在后台成片编辑器里改；其余版本、卡点、跨场次呼应还没做 |
| 渲染 | GPU 上的 Remotion | 同一台 CPU 机器上的 Remotion，字幕样式在后台配置 |
| 梗库 | meme 表 + 向量检索 + 每日抓 B站热门 | 没有向量检索，不抓热门。梗从多场转写和弹幕里用 n-gram 挖掘（至少 2 场都有），后台可删、手动加、“转正”并入主播档案（热词、字幕、标签、提示词都会用） |
| 审核 | 通过 / 拒绝、多版本预览 | Y / N + 一键原因 + 盲审 / 快审 + 耗时记录，见模块八 |
| 发布与数据回流 | 发布辅助、每日录入播放数据、LightGBM 排序 | 发布包（封面、标题、简介、标签）复制粘贴，上传 B站手动；切片号投稿按 BV 号绑定，播放数据回流到精排记忆；排序权重是手工公式，攒够数据后由后台建议新权重，没有 LightGBM |

重计算只落在少量候选上：整场只跑便宜的统计粗筛，多模态大模型只处理 20–30 个窗口，整场转写同时写入全文索引供跨场次呼应使用。每位主播的布局模板、风格包和词库贯穿第 3–6 步。

## 模块一：采集与预处理

直播时同步录制视频和弹幕，统一用**开播时刻的墙钟时间**作为时间原点，下播后自动触发处理。合作主播提供的本地录像和分轨音频质量更高，优先使用。

1. **开播检测**：每 30 秒轮询主播直播间状态，开播即启动录制和弹幕采集，创建一条“场次”记录。
2. **视频录制**：用录播姬（BililiveRecorder）或 blrec 拉取原画流，按 FLV 分段落盘；断流重连时记录每段的真实起始时间。
3. **弹幕采集**：连接直播间弹幕 WebSocket，把弹幕、礼物、SC、上舰统一写成 JSONL：`{ts, type, uid_hash, text, value}`。用户 ID 只存哈希，不存昵称。
4. **下播后预处理**：FFmpeg 无损合并分段并转封装为 MP4；抽取 16kHz 单声道音轨供识别用；生成每 2 秒一帧的低分辨率缩略图供画面分析。
5. **主播画面布局**（每位主播配置一次）：动漫人脸检测模型自动标出 Live2D 模型和脸部位置，人工在后台框选确认模型区、游戏区和挂件区，存为布局模板；主播换皮或改布局时重新确认。

录制和弹幕协议依赖开源项目和非官方接口，实施前需确认可用性；合作主播可直接用 OBS 多轨录制，从根本上绕开拉流。

## 模块二：有趣片段识别

先用便宜信号从整场中筛出 20–30 个候选窗口，再只对候选做语音转写和多模态大模型判断，最终保留 5–10 条。

### 第一步：粗筛

整场按 10 秒分桶，每桶计算以下信号，各自相对本场均值做 z-score 归一化后加权。

| 信号 | 计算方式 | 对应的有趣时刻 | 初始权重 |
| --- | --- | --- | --- |
| 弹幕密度 | 桶内弹幕数 ÷ 前 5 分钟滑动均值 | 爆笑、翻车、名场面 | 0.30 |
| 弹幕情绪词 | 命中 VTuber 圈词典（草、绷、哈哈哈、？？？、切片 等）及主播专属梗的占比 | 观众明确在笑或在怀疑 | 0.25 |
| 礼物 / SC | 桶内金额取对数 | 读 SC、互动名场面 | 0.10 |
| 音频事件 | 人声轨响度突增 + 笑声/尖叫检测 | 破防、大笑、被吓 | 0.25 |
| 画面变化 | 缩略图帧差与镜头切换数 | 游戏高能、画面剧变 | 0.10 |

- **弹幕延迟校正**：观众反应比画面慢 3–10 秒，弹幕类信号整体前移；前移量每场用音频峰与弹幕峰的互相关自动估算。
- **取峰**：综合分经 30 秒平滑后做峰值检测，间隔小于 60 秒的峰合并，取 Top 20–30 作为候选，每个候选前后各扩 90 秒。
- **歌回过滤**：音乐检测判定为唱歌的时段直接排除。

### 第二步：转写与精排

1. **语音转写**：对整场人声用 FunASR（Paraformer，中文口语效果好）转写，输出词级时间戳；主播口头禅、梗、游戏术语配置为热词。日语或中日混说的主播换用 faster-whisper。
2. **多模态大模型判断**：输入「逐字稿 + 弹幕采样 + 礼物事件 + 窗口内 8–16 张抽帧 + 前后 2 分钟摘要」，要求返回 JSON：
   - 是否有趣、脱离直播能否看懂
   - 类型（破防 / 口胡 / 互动 / 金句 / 高能）和 1–10 分
   - 笑点发生的精确时间点（供运镜用）
   - 建议起止句
3. **排序**：最终分 = 0.4 × 粗筛分 + 0.6 × 大模型分，去重后取前 5–10 条。积累几百条审核记录后，用 LightGBM 排序模型替代这个手工公式。
4. **边界修正**：按词级时间戳对齐到句子边界；起点前留 1–3 秒铺垫，终点延到笑声结束或弹幕密度回落；时长控制在 30 秒到 3 分钟。

## 模块三：剪辑脚本与风格化包装

大模型当“剪辑导演”：读完片段后输出一份**带时间点的 JSON 剪辑脚本**，渲染器只负责执行。脚本只能引用模板库里已有的效果和素材 ID，渲染前用 JSON Schema 校验，不合法的事件丢弃。

```json
{
  "clip_id": "S20261109-03",
  "range": [5321.4, 5388.9],
  "layout": "game_top_model",
  "title_candidates": ["…", "…", "…"],
  "events": [
    {"t": 5323.0, "type": "slow_push", "to": 1.08, "dur": 6.0},
    {"t": 5330.2, "type": "punch_in", "target": "face", "scale": 1.6, "dur": 0.4},
    {"t": 5330.2, "type": "caption", "style": "boom", "text": "破防了"},
    {"t": 5330.3, "type": "sfx", "id": "boom_01"},
    {"t": 5335.5, "type": "sticker", "id": "emote_cry", "pos": "top_right", "dur": 1.5},
    {"t": 5341.0, "type": "shake", "intensity": 0.6, "dur": 0.5},
    {"t": 5384.0, "type": "end_card"}
  ]
}
```

### 效果模板库

| 效果 | 触发时机 | 实现要点 |
| --- | --- | --- |
| 推镜 punch\_in | 笑点或反转落下 | 以模型脸部为中心，0.3–0.5 秒放大到 1.3–2 倍，缓动曲线，停留后回弹 |
| 缓推 slow\_push | 讲故事、铺垫 | 数秒内放大 5%–10% |
| 震屏 shake | 尖叫、拍桌 | 跟随音频峰值，位移和旋转小幅随机抖动 |
| 定格 freeze | 名场面瞬间 | 冻结 1–1.5 秒，叠大字和音效 |
| 综艺花字 caption | 关键句、吐槽 | 按情绪选样式：爆炸字、颤抖字、手写体，配色取主播主题色 |
| 表情贴纸 sticker | 情绪高点 | 优先主播官方表情包，素材按情绪标签（哭、怒、问号、得意）入库 |
| 音效 sfx | 配合花字和运镜 | 使用商用授权音效库，按情绪分类 |
| 弹幕飘屏 danmaku | 观众刷屏时 | 取当时高频的真实弹幕放大飘过 |
| 脑补配图 image | 主播描述某个画面 | 先从授权图库检索；用 AI 生成的配图在画面上标注 |
| 片尾引流卡 end\_card | 结尾 3–5 秒 | 主播立绘、名字、直播间号、直播时间表、关注引导 |

- **密度约束**：同一时刻最多叠两种效果，每 10 秒最多一次推镜，避免画面过吵；约束写在提示词里，校验时也再校一遍。
- **画质保障**：放大超过 1.5 倍时，先用 Real-ESRGAN 动漫版超分处理模型区域，再放大。
- **主播风格包**：每位主播一套配置，包括主题色、字体、贴纸库、片尾卡和口头禅词库，保证同一主播的切片风格统一、有辨识度。

## 模块四：流行梗与二创

在基础包装之上，给切片加入**恰到好处的流行梗和二创元素**：每条切片 1–2 个梗，必须贴合当下情境，宁缺毋滥。做法是维护一个梗库，写剪辑脚本前先检索匹配，再由大模型决定用不用、用在哪。

### 梗库：从哪来、怎么存

- **来源**
  - B站热门、每周必看、热搜：每天抓取标题和热评里的高频短语。
  - 梗百科类站点（如萌娘百科、小鸡词典）：补充出处和用法。
  - VTuber 圈和主播本人的梗：对历史弹幕做新词发现，找出突然高频的短语，由运营确认入库。
  - 运营人工补充。
- **每条梗的记录**：名称、出处、含义、适用情境、情绪标签、示例用法、可用形式（字幕 / 贴纸 / 音效 / 模板）、热度、首次出现时间、尺度等级。
- **热度衰减**：按近 7 天的出现频次更新热度，热度跌破阈值自动降权，避免用过气梗。
- **准入审核**：新梗要人工确认含义和尺度后才能被自动使用；低俗、地域攻击、政治敏感、拿真人不幸开玩笑的梗进黑名单。

### 匹配：让梗用在对的地方

1. 大模型先给片段写一句情境描述，如“主播自信满满，结果秒输，弹幕狂刷问号”。
2. 用文本向量在梗库里检索 Top 10 候选。梗库在几千条以内时，在 Python Worker 内存里做向量检索即可，不需要向量数据库。
3. 大模型从候选中挑 0–2 个，给出使用位置、形式和理由；说不清“这里为什么好笑”就不用。
4. 主播可以在配置里禁用某类梗或某个具体的梗。

### 表现形式

| 形式 | 例子 | 实现 |
| --- | --- | --- |
| 梗字幕 | 吐槽花字用流行语改写；空耳、谐音字幕 | caption 事件 + 梗化文案 |
| 梗图贴纸 | 经典梗图格式，用主播形象重绘 | 授权或自制素材入 asset 库，关联梗 ID |
| 梗音效 | 流行音效在笑点响起 | 只用有商用授权的音效库或自制音效 |
| 剪辑模板 | “我以为…结果…”反转、前方高能预警、名场面三连重放、倒放、慢动作回放、“说 vs 做”分屏 | Remotion 模板组件，脚本用 template 事件调用 |
| 二创插画 | Q 版、手书风的主播形象插画，用作转场或配图 | 经主播授权，用其立绘训练图像风格模型（如 LoRA）生成，画面标注 AI 生成 |
| 衍生物料 | 从名场面自动截图做表情包、语录卡片，供粉丝传播 | 随切片一起产出、一起审核 |

剪辑脚本里对应增加三类事件：

```json
[
  {"t": 5329.0, "type": "template", "id": "expect_vs_reality", "args": {"expect": "稳了", "reality": "秒输"}},
  {"t": 5331.2, "type": "meme_caption", "meme_id": "m_0412", "text": "…"},
  {"t": 5333.0, "type": "replay", "times": 3, "speed": [1.0, 0.75, 0.5]}
]
```

### 防止“尬”和翻车

- **密度**：每条最多 2 个梗，每 15 秒最多 1 个；梗不能盖过主播本身的笑点。
- **圈层**：B站观众熟悉 VTuber 圈和二次元梗，优先用这些；发到其他平台时多用大众梗。
- **审核**：审核后台单独列出本条用到的梗和理由，可一键替换或移除。
- **数据**：记录每个梗的使用次数、审核保留率和所在切片的完播率，表现差的梗降权。
- **版权**：不直接截取影视、综艺、歌曲原片段做梗；用模板复刻形式，或使用自制、授权素材。抓取热门内容只用于提炼梗的文字信息，控制频率。

## 模块五：创意与叙事增强

目标是让切片“有活儿”：每条切片是一个有起伏的小故事，能跨场次前后呼应，有固定栏目和吐槽口吻。这些能力全部落在剪辑脚本里，渲染器只是多了几个模板组件。

### 1. 故事结构

- **三段式**：精排时大模型同时标出铺垫（setup）、笑点（punch）、余韵（aftermath，如主播补刀、弹幕集体反应），边界修正以此为准，余韵默认保留。
- **倒叙开头**：笑点足够强时，先放 1–2 秒结果，再打“十秒前……”回到开头。

### 2. 跨场次呼应

- **整场转写入库**：每场人声全部转写，按句写入 `transcript_segment` 表，用 MySQL 5.7 的 ngram 全文索引支持中文检索。
- **找呼应素材**：精排后用片段关键句和主播梗百科检索历史场次，找三类：立 flag 与打脸、口头禅重复、同一话题的前后反转。
- **生成呼应版**：命中后，历史片段作为插叙或开头，配“X 月 X 日，她说……”字幕。

### 3. 主播梗百科

`streamer_lore` 记录人设、口头禅、粉丝昵称、名场面和圈内梗，作为大模型的固定上下文，让它写出“自己人才懂”的笑点。由运营维护，也可从粉丝时间轴和评论区提炼候选。

### 4. 新增表现手法

| 手法 | 脚本事件 | 说明 |
| --- | --- | --- |
| 倒叙开头 | cold\_open | 先放结果，再回到铺垫 |
| 弹幕对话 | chat\_bubbles | 真实弹幕做成对话气泡或群聊截图，与主播一来一回 |
| 伪 UI | ui\_popup | “成就解锁：第一次破防”弹窗、随情绪变化的血条 |
| 吐槽旁白 | narration | 固定口吻的文字旁白，口吻写在账号风格配置里 |
| 卡点 BGM | bgm、beat\_cut | 授权曲库按情绪选曲，用 librosa 检测鼓点对齐剪辑点 |
| 留白 | silence\_drop、hold | 笑点前抽掉音乐，笑点后留 0.5–1 秒反应 |
| 鬼畜点缀 | remix | 重复、变调、卡点，每条最多一处，需主播授权 |

### 5. 多版本与栏目

- **多版本**：每条切片生成 2–3 个版本：纯享版（少包装）、综艺版（花字、运镜、梗）、整活版（鬼畜、伪 UI 更多）。先出低清预览供审核挑选，选定后再出高清。
- **固定栏目**：如《kiya 迷惑行为大赏》《本周破防集锦》《kiya 语录》，每个栏目一套片头、封面和旁白口吻；每周自动汇编合集。

### 6. “好活”范例库

- 审核时把好的手法标记为“好活”，`craft_example` 存切片、手法标签和播放数据；表现最好的几条作为大模型的参考示例。
- 定期拆解同类头部切片号的爆款，统计开头 3 秒做法、平均镜头时长、梗密度，写成风格参数。

**节制原则**：包装服务于主播。每条切片的特效、梗和伪 UI 合计有上限，纯享版始终保留作为审核兑底。整场转写和多版本预览使每场 GPU 时长增加约 0.25–0.5 小时，已计入成本估算和选型表。

## 模块六：渲染与输出

第一版只做 **Remotion 自动成片**，审核时直接改脚本重新渲染，不依赖剪辑师。**剪映草稿**留作扩展：后续有剪辑师加入时，从同一份脚本生成剪映工程供精修，上游不用改动。

1. **素材准备**：FFmpeg 按 `range` 精确切出片段（重新编码，避免关键帧问题），同时导出人声轨和游戏/BGM 轨；字幕由 ASR 结果经大模型纠错后生成逐词时间轴。
2. **Remotion 成片**：用 React 写视频模板，每种效果一个组件（`PunchIn`、`Shake`、`Caption`、`Sticker`、`EndCard`…），输入是剪辑脚本 + 主播风格包 + 布局模板。竖屏布局两种：
   - `game_top_model`：上方模型放大，下方游戏画面，字幕在中缝
   - `model_center`：杂谈场景，模型居中，背景用主题色或虚化
3. **音频处理**：音效出现时自动压低游戏/BGM 轨；整体响度归一化到短视频平台常用的 -14 LUFS 左右。
4. **编码输出**：1080×1920、30fps、H.264；有 NVIDIA 显卡时用 NVENC 加速。
5. **剪映草稿**：（后续启用）用开源库（如 pyJianYingDraft）把片段、字幕、贴纸、音效和关键帧缩放写成剪映工程，剪辑师在剪映里打开就能继续改。需先确认该库支持你安装的剪映版本。
6. **封面与标题**：从片段里挑模型表情最夸张的一帧，叠大字标题和主播名做封面；大模型以同类爆款标题为参考生成 3 个候选标题和话题标签。

Remotion 对一定规模以上的公司收费，商用前需确认许可。如果不想用 React 渲染，可退而用 Python 的 MoviePy 或 FFmpeg 滤镜实现，但运镜和花字动画会难写很多。

## 模块七：审核与引流发布

审核后台的目标是**每条切片 5 分钟内处理完**，并把每次人工修改记录下来，用于优化识别和包装。

- **切片列表**：按场次展示候选，显示分数、类型、时长和大模型给出的理由。
- **预览与微调**：播放成片；拖动起止点；以时间轴展示脚本事件，可逐项开关、改花字文字、换贴纸；修改后一键重新渲染。
- **选标题和封面**：从 3 个候选中选或手改。先在 2–3 个剪辑版本中选定一个再出高清；好的剪辑手法可一键标记为“好活”，存入范例库。
- **结论**：通过 / 拒绝（选拒绝原因：不好笑、看不懂、边界差、包装过度、不能发）/ 转剪辑师精修（剪辑师加入后启用；第一版由运营自己在后台微调脚本后重新渲染）。
- **发布**：第一版下载成片和文案后，手动发布到自己的切片号，简介注明“非官方切片”并附主播空间链接；标题和简介统一带上主播名、直播间链接和原场次时间。发布后把视频链接回填到后台。
- **数据回收**：每天录入或导入各切片的播放、完播率、点赞、涨粉数据，对应到切片和脚本版本。
- **主播端（可选）**：给合作主播一个只读入口，可以标记“不要发”的片段和不能切的话题。

## 模块八：反馈闭环与运营（已实现）

这一块是原方案没有写、实现过程中加的：让审核、剪辑和投稿数据反过来改进系统，并给主播一份能看懂的报告。原则：会改变行为的闭环都有“攒够 N 条才生效”的门槛，不拿一场数据调阈值或提示词；候选不凑数，没有过线的片段就不出；上传 B站始终由人手动。

### 边播边筛

.env 里 KIYA\_LIVE\_SCREEN=1（默认关）后，监控脚本在直播中每 30 分钟对已录完的分段跑一次 screen.py --live（nice 低优先级，录制优先）。只出候选：不转写、不精排、不剪切，审核页顶部标“临时结果”，编辑成片等下播后再做。各分段的音频和画面特征单独缓存在 segfeat/，下播后的正式粗筛整体覆盖临时结果，只需提取最后一段；已标的 Y/N、原因、耗时按片段起点 5 秒内对应到新候选上，对不上的才丢弃。

### 审核反馈

审核页每条可点一键原因（开头 / 结尾太早太晚、不好笑、要前情才懂、只是念醒目留言、重复的梗、主播不想发、特别好笑），并记录审核耗时（单次最多算 10 分钟）。分盲审（先自己判断）和快审（看着 AI 判，AI 很有把握可一键采纳）两种模式：只有盲审的标注进评测和权重校准，快审只当例子，采纳 AI 的不用于任何统计。开头 / 结尾边界的反馈攒够 8 票且一边倒（70% 以上）才提示调粗筛前后秒数，只是建议，不自动改配置。

### 剪辑口味

AI 初稿另存为 edits/NN.ai.json，人保存终稿后两者对比（同类效果按绝对起点 2 秒内匹配），统计保留、删除、新增和移动。攒够 5 条且来自 2 场以上才把口味写进初稿提示词（edit\_v2）；直接恢复 AI 初稿或没动过的不算人工修改。

### 精排记忆、梗转正和禁区

learn.py 在下播后（精排前）更新 memory.json：反复出现的说法（至少 2 场）、审核例子、主播和切片号的最新投稿、按类型汇总的切片播放表现（绑定满 5 条 BV 号才用）；攒够 3 场“精排 + 盲审标注”后在历史数据上搜一组更好的排序权重，更好才建议，后台确认才生效。每次精排都记录用的是哪一版记忆。后台的决定存在 config/memory\_decisions.json，kiya.yaml 本身不被改写。梗可以“转正”并入主播档案；禁区话题命中的片段精排总分为 0、排到最后，审核页标红，增删禁区词会自动重算所有已精排的场次。

### 主播周报

后台“主播周报”页（weekly\_report.py，纯本地统计，不调大模型）：本周最火的梗 TOP5（含较上周涨跌）、高光场面、哪类内容更出效果（高光攒够 5 个才出占比，切片播放表现要绑定满 5 条才有）、观众弹幕词云。一键导出单个 HTML 文档给主播，只含适合主播看的内容，不含审核备注、通过率、禁区话题和场次编号；禁区命中的、审核标了不有趣的片段不会出现。

**任务链（Redis Stream）**：每一步是一种 job，上一步成功后由 Spring Boot 创建下一步：

1. `PREPROCESS`（合并、抽音轨、抽帧）
2. `COARSE_SCREEN`（粗筛，写 `candidate`）
3. `TRANSCRIBE`（整场人声转写，写入全文索引）
4. `LLM_RANK`（写分数和故事结构，检索历史场次找呼应素材，创建 `clip`）
5. `SCRIPT`（检索梗库和主播梗百科，每条生成 2–3 个版本的剪辑脚本并校验）
6. `RENDER`（先渲染各版本低清预览，审核选定后渲染高清）
7. 进入 `PENDING_REVIEW`，等待人工审核

job 状态为 `PENDING → RUNNING → SUCCESS / FAILED`，失败最多重试 3 次，每一步幂等（重跑前清理本步产物）。Python Worker 从流中消费，完成后调用 Spring Boot 的回调接口 `POST /internal/jobs/{id}/result` 写回结果。

另有每日定时任务 `MEME_REFRESH`：抓取 B站热门和热搜、更新梗的热度，并把从弹幕里新发现的候选梗推给运营确认。

每周定时任务 `SERIES_COMPILE`：按栏目从本周通过的切片里自动组合合集脚本，进入审核。

## 技术栈与部署

第一版**全部部署在云上**：一台常驻 CPU 云服务器负责录制、业务和粗筛，GPU 按场次按量租用、处理完自动释放。CPU 服务器、对象存储和 GPU 放在同一云厂商的同一地域，走内网传输，避免公网流量费。

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 业务后端 | Spring Boot 3 + MyBatis-Plus + MySQL | 主播、场次、切片、审核、任务编排 |
| 队列 / 缓存 | Redis（Stream） | 任务分发，开播状态缓存 |
| 对象存储 | 云对象存储（与 GPU 同地域） | 录像、弹幕、素材、成片 |
| 录制 | 录播姬 / blrec + Python 弹幕采集器 | 常驻在 CPU 云服务器上 |
| 处理 Worker | Python 3.11：FFmpeg、FunASR、faster-whisper、PySceneDetect、音频事件检测、动漫人脸检测、Real-ESRGAN | 部署在按量 GPU 实例上 |
| 大模型 | 通过 API 调用支持图片输入的多模态模型（如通义千问 VL 系列）+ 纯文本模型（如 DeepSeek） | 精排和写脚本用多模态，标题和字幕纠错用纯文本 |
| 渲染 | Node.js + Remotion；剪映草稿（pyJianYingDraft）待剪辑师加入后启用 | 渲染服务也从队列消费，部署在按量 GPU 实例上 |
| 审核后台 | Vue 3 或 React + 视频播放器与时间轴组件 | 网页版；以后可用 Tauri 2 包成桌面端 |
| 梗库检索 | 文本向量 API + Python 内存检索 | 梗库几千条以内，不需要向量数据库 |

**云资源配置（支撑 2–3 位主播，后续按需升级）**

- **常驻 CPU 服务器**：4 核 8GB（经济型 e，ecs.e-c1m2.xlarge），运行 Spring Boot、MySQL、Redis、录制和弹幕采集，以及预处理和统计粗筛（弹幕统计、音频响度、镜头切换检测用 CPU 就能跑）。挂 100GB 云盘作录制缓冲，录完上传对象存储。
- **按量 GPU 实例**：单卡 24GB 显存一档（如 RTX 4090 / A10），跑语音转写、超分、Remotion 渲染和 NVENC 编码。
- **只把候选送上 GPU**：粗筛在 CPU 服务器完成，只把 20–30 个候选窗口（约 2–3 GB）交给 GPU，而不是整场约 11 GB 录像，GPU 计费时长和传输量都大幅减少。
- **启停策略**：队列里有 GPU 任务时，由 Spring Boot 调云厂商 API 开机，空闲 10 分钟自动关机；依赖和模型权重预装在自定义镜像或数据盘上，开机后几分钟内可用。多位主播下播时间接近时，任务排队共用同一实例。
- **对象存储**：录像、弹幕、素材、成片统一存放；原始录像设生命周期规则，14 天后自动删除。
- **网络**：拉直播流进云服务器属于入方向流量，云厂商通常不收费；审核时下载成片走出方向，量很小。注意：3 路同时录制约需 18Mbps 入带宽，而出带宽不超过 10Mbps 的实例入带宽通常也被限在 10Mbps 左右；建议公网选“按使用流量”并把峰值设到 30Mbps 以上（出方向流量很少，费用低），购买前向阿里云确认。

**升级路径**：超过 3 位主播时，服务器升到 4 核 16GB 或 8 核，GPU 改为多实例并行，其余架构不变；阿里云 ECS 支持直接升配，不用重新部署。

## 效果保障与指标

效果好坏取决于有没有“标准答案”和闭环：**先建评测集，每次改动都跑分，发布数据再反哺排序和包装**。

- **评测集**：每位合作主播标注 5–10 场。标注来源包括粉丝在 B站录播评论区整理的“高能时间轴”、已有切片号的爆款视频（回溯到原场次时间点），以及主播本人的标记。
- **提示词与模板版本化**：大模型提示词、信号权重和效果模板都带版本号，切片记录生成时用的版本，便于对比效果。
- **定期重训**：审核记录和发布数据每周用于重新拟合权重或排序模型。
- **A/B**：同一类切片轮换封面风格、开头是否加钩子、特效密度，比较完播率和点击率。

| 指标 | 衡量什么 | 来源 | 建议起始目标 |
| --- | --- | --- | --- |
| Top 10 命中率 | 识别准不准 | 评测集 | ≥ 50% |
| 审核通过率 | 产出能不能直接用 | `review_log` | ≥ 60% |
| 单条人工耗时 | 自动化程度 | `review_log.cost_seconds` | ≤ 5 分钟 |
| 特效关闭率 | 包装是否合适 | 脚本修改差异 | 持续下降 |
| 完播率、3 秒跳出率 | 观众爱不爱看 | 平台创作中心 | 以前 2 周为基线提升 |
| 引流关注 | 宣传效果 | 主播后台涨粉与切片发布时间对照 | 与主播商定 |
| 梗保留率 | 梗用得对不对 | clip\_meme.kept | ≥ 70% |
| 版本胜率 | 哪种剪法更受欢迎 | clip\_variant.chosen + 播放数据 | 用于调整默认版本 |
| 栏目完播率 | 固定栏目是否形成辨识度 | 平台创作中心，按 series 汇总 | 高于单条切片均值 |

目标值是起步建议，跑完前 10 场后用真实数据重新设定。

## 风险、合规与待确认事项

最大的风险是**授权和平台规则**，技术上都有可行解；第一版只和签了切片授权的主播合作，可以规避大部分风险。

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 切片未授权 | 侵权投诉、封号 | 与主播或其公会签书面授权，写明切片、立绘、表情包的使用范围 |
| 游戏画面、BGM、歌曲版权 | 平台版权检测限流或下架 | 不切歌回；使用分轨素材时去掉或压低 BGM；游戏按厂商直播政策处理 |
| 字体、音效、配图授权 | 商用侵权 | 素材库只收录有商用授权的素材，`asset.license` 必填 |
| 弹幕和拉流接口变更 | 采集中断 | 合作主播优先用本地 OBS 录像；采集器加心跳告警 |
| 断章取义、涉及私人话题 | 伤害主播形象 | 人工审核；主播可配置禁切话题；大模型判断“脱离上下文是否有歧义” |
| 观众个人信息 | 隐私风险 | 用户 ID 只存哈希；弹幕飘屏不显示昵称 |
| AI 生成内容 | 平台标识要求 | AI 生成的配图在画面上标注，发布时按平台要求勾选声明 |
| 梗用错、过气或尺度不当 | 尴尬、引起反感、伤主播形象 | 新梗人工准入、热度衰减、黑名单、每条最多 2 个、审核时单列可移除 |
| 按量 GPU 缺货或开机慢 | 出片延迟 | 配置两个可用区或备用机型；任务在队列里等待，不影响录制 |

以上不构成法律意见，商用前建议咨询专业人士。
