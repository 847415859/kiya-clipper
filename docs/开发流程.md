# 开发流程

## 总览

从今天开录到稳定运营，业余一人约 **13 周**，分五个阶段。每个阶段只有过了验收门槛才进入下一阶段，没过就先优化当前阶段。录制从第一天起持续运行，不随阶段暂停。

| 阶段 | 时间 | 目标 | 主要代码 | 验收门槛 |
| --- | --- | --- | --- | --- |
| 0 准备与验证 | 第 0–1 周 | 开录、拿授权、开账号、手工验证核心假设 | 几个 Python 小脚本 | 弹幕高峰大部分对应有趣片段；手工切片有正向反馈 |
| 1 最小链路 | 第 2–3 周 | 录像 → 粗筛 → 横屏切片 | `worker/` | 3 场回放里过半候选确实有趣 |
| 2 识别与脚本 | 第 4–6 周 | 整场转写、多模态精排、剪辑脚本 | `worker/` | 评测集 Top 10 命中率 ≥ 50%，脚本 100% 通过校验 |
| 3 包装与平台 | 第 7–10 周 | Remotion 模板、Spring Boot 编排、审核后台、上云 | 全部四个目录 | 审核通过率 ≥ 60%，单条 ≤ 5 分钟，下播 1 小时内出片 |
| 4 创意与闭环 | 第 11–13 周 | 跨场次呼应、梗库、栏目、发布与数据回流 | `worker/`、`backend/` | 连续 2 周稳定出片，引流数据可追踪 |

先用 Python 跑通算法、再搭 Spring Boot 平台，是为了在工程投入最大的阶段 3 之前，先用数据证明“能找准、能剪好”。阶段 1–2 的 Python 代码会原样变成阶段 3 的 Worker，不会白写。

## 阶段 0：准备与手工验证（第 0–1 周）

**目标**：数据开始积累，外部依赖全部打通，并用一周时间验证两个核心假设：弹幕高峰就是有趣时刻；这种包装风格有人看。

### 0.1 今天就开始录制

- [x] 在本机或一台便宜服务器上用 Docker 部署录播姬（BililiveRecorder）
- [x] 添加娜由纪雅kiya（UID 646830928）的直播间，开启自动录制、保存弹幕和礼物（XML）
- [ ] 画质选原画，按 30 分钟分段，确认磁盘空间至少够存 5 场
- [ ] 录完一场后检查：视频可播放、弹幕时间与画面对得上

### 0.2 合作与授权

- [ ] 和主播沟通切片合作，拿到书面授权，写明范围：切片、立绘、表情包、二创、鬼畜
- [ ] 询问能否提供 OBS 分轨录像和官方素材（表情包、立绘、主题色）
- [ ] 询问是否愿意分享涨粉数据，并约定“不能切的话题”

### 0.3 账号与环境

- [ ] 阿里云：实名认证，暂不购买资源；用价格计算器核对方案报价

- [x] AutoDL：注册并确认能否用 API 开关机，以此定下选方案 D 还是全阿里云
- [ ] 开一个自己的 B站切片号，简介写明“非官方切片”
- [x] 本机安装 Python 3.11、FFmpeg、Node.js、Docker；建 Git 仓库 `kiya-clipper`，建好六个目录

AutoDL 结论（2026-11-09）：官方 API 只支持“容器实例 Pro”，需实名认证；开发者 Token 已调通。但当晚西北 B 区 4090 / 5090 全部租满，抢卡风险大。阶段 3 主方案用全阿里云，AutoDL 作为“先试、10 分钟无卡改用阿里云”的省钱选项，届时按晚 11 点后的实测库存决定。

### 0.4 手工验证

1. 录到 2–3 场后，写一个小脚本画出弹幕密度曲线，对照回放看前 20 个高峰，记录每个是否有趣。
2. 手工用剪映剪 3 条带推镜、花字、梗的竖屏切片，发到切片号，观察一周内的完播率和评论。
3. 把每条手工切片用到的手法记下来，作为后续效果模板库的第一批需求。

### 0.5 评测集起步

- [ ] 收集粉丝在录播评论区整理的时间轴，和已有切片号的爆款视频
- [ ] 在 `eval/` 里用统一格式保存：`{session, start_s, end_s, type, note}`
- [ ] 开始记录主播梗百科：人设、口头禅、粉丝昵称、名场面

**交付物**：持续录制的录像和弹幕；书面授权；验证记录；第一版评测集和梗百科。

**验收**：前 20 个弹幕高峰中有一半以上确实有趣；手工切片有正向反馈。如果弹幕高峰不准，先调整信号设计再进阶段 1。

## 阶段 1：跑通最小链路（第 2–3 周）

**目标**：对已录好的文件，一条命令输出 20–30 个候选片段和对应的横屏小视频。只写 `worker/`，在本机运行，不上云。

### 1.1 工程骨架

- [x] `worker/` 用 venv + requirements.txt 管理依赖；为保持简单，命令行用 argparse、数据结构用 dataclass，信号处理用 numpy / scipy
- [x] 统一数据结构：`Session`、`DanmakuEvent`、`Candidate`，所有脚本的输入输出都是 JSON 文件
- [x] 配置文件 `config/kiya.yaml`：信号权重、弹幕词典、分桶大小

### 1.2 四个核心脚本

1. `preprocess.py`：合并 FLV 分段并转封装 MP4；抽 16kHz 单声道音轨；每 2 秒抽一帧缩略图；记录每段真实起始时间。
2. `parse_danmaku.py`：解析录播姬 XML，输出 JSONL；按 10 秒分桶统计弹幕数、情绪词占比、礼物金额。
3. `signals.py`：计算音频响度曲线和画面帧差；估算弹幕延迟并平移；各信号 z-score 归一化后加权。
4. `screen.py` + `cut.py`：平滑后做峰值检测、合并相邻峰，输出候选 JSON；再用 FFmpeg 剪出每个候选的横屏片段，文件名带时间和分数。

### 1.3 评测与调参

- [x] 写 `evaluate.py`：对比候选与 `eval/` 标注，输出 Top 10 / Top 20 命中率
- [x] 画一张信号图（matplotlib）：各信号曲线 + 候选点 + 标注点，用来直观调权重
- [ ] 调整权重和弹幕词典，每次改动都跑一遍评测并记录结果
- [x] 给信号计算和峰值检测写单元测试（pytest），用一小段固定样例文件

进度（2026-11-09）：阶段 1 代码已完成并用合成录像测试通过——`screen.py`（弹幕 + 音频响度 + 画面变化，弹幕延迟自动估计）、`cut.py`（跨分段精确剪切）、`evaluate.py`（命中率 / 召回率并记录 results.csv），下播后监控会自动跑粗筛。剩下“用真实场次调权重和词典”，等录满 3 场并完成标注。

**交付物**：`worker/` 可运行的粗筛链路；评测脚本；第一版权重配置。

**验收**：3 场回放里过半候选确实有趣；一场 4 小时录像的粗筛在普通电脑上 15 分钟内完成。

**常见坑**：断流重连导致弹幕错位；FFmpeg `-c copy` 剪切开头花屏（要重新编码）；弹幕密度受开播初期“打招呼”影响，要用滑动均值而不是全场均值。

## 阶段 2：转写、精排与剪辑脚本（第 4–6 周）

**目标**：精排后的 Top 10 更准，每条切片有合法的 JSON 剪辑脚本。仍在本机运行，GPU 步骤可以临时租一台 AutoDL 或阿里云按量实例。

### 2.1 转写

- [x] 接入 FunASR（Paraformer），输出带词级时间戳的逐字稿；主播口头禅和梗配置为热词
- [ ] 抽测 10 分钟转写结果，字错率太高时尝试 faster-whisper 对比
- [x] 整场转写按句存为 JSONL，为阶段 4 的全文索引做准备
- [x] 接入音频事件检测（笑声、尖叫）和音乐检测，分别用于粗筛加分和歌回过滤

### 2.2 多模态精排

- [x] 封装大模型调用层 `llm/`：统一接口、可切换模型、请求和响应落盘缓存、失败重试
- [x] 精排提示词 v1：输入逐字稿、弹幕采样、礼物事件、抽帧、前后摘要和主播梗百科；输出分数、类型、笑点时间、故事结构、起止句
- [x] 用 pydantic 校验模型输出，不合法就重试一次再丢弃
- [x] 实现排序公式和边界修正（对齐句子、保留铺垫和余韵、时长 30 秒到 3 分钟）
- [x] 提示词放在 `prompts/` 并带版本号，每次改动都跑评测集比较

### 2.3 剪辑脚本

- [x] 定义剪辑脚本的 JSON Schema（含效果、梗、模板事件），放在仓库根目录 `schema/`，供 Python 和 Remotion 共用
- [x] 脚本生成提示词 v1：先只生成综艺版，效果限定在推镜、震屏、花字、贴纸、音效、片尾卡
- [x] 写校验器：Schema 校验 + 密度约束（同时最多两种效果、每 10 秒最多一次推镜）+ 素材 ID 存在性
- [x] 用 FFmpeg 做一个简易预览：只叠字幕和花字文字，先人工判断脚本写得好不好，不等 Remotion

进度（2026-11-10）：阶段 2 开发完成，13 项里勾了 12 项；只剩“抽测转写”要你手工听写一段做参考文本，工具 `asr_eval.py` 已经写好（算字错率，列出最常错的词）。fun-asr 效果明显好于 paraformer，暂时不需要 faster-whisper。说明：转写走百炼 fun-asr（不用 GPU，约 ¥2/场）；音频事件用信号处理 + 转写文本实现，没有另接模型。笑声、尖叫已经计入粗筛；歌回过滤默认关闭，等看过真实数据再定阈值。精排用 `rerank.py`，提示词 `prompts/rerank_v1.md`，输出用 pydantic 校验，请求结果有缓存；`autoedit.py` 生成剪辑初稿；密度约束会在保存时提醒、在自动生成时强制执行。后台已经接上精排、AI 初稿和精排对比。这些都只用假接口测过，还没有调过真实大模型。验收门槛（Top 10 命中率 ≥ 50%）要等攒满 3 场标注后，用“精排对比”来判断。

**交付物**：转写、精排、脚本生成的完整命令行链路；版本化的提示词；剪辑脚本 Schema。

**验收**：评测集 Top 10 命中率 ≥ 50%，并明显高于阶段 1；脚本 100% 通过校验；单场大模型费用在预算内。

**常见坑**：大模型对时间点的输出常偏差几秒，要用逐字稿时间戳二次对齐；抽帧太多会拉高费用，先用 8 张；开头就做好缓存，调提示词时不重复花钱。

## 阶段 3：包装、平台与上云（第 7–10 周）

**目标**：从“命令行工具”变成“无人值守的系统”：下播后自动出片，在审核后台里 5 分钟内处理完一条。这是工程量最大的阶段，按下面顺序做。

### 3.1 Remotion 渲染（第 7–8 周）

- [ ] `renderer/` 初始化 Remotion + TypeScript，从 `schema/` 生成剪辑脚本的类型定义
- [ ] 实现两种竖屏布局：`game_top_model`、`model_center`
- [ ] 按使用频率实现效果组件：字幕 → 推镜 / 缓推 → 花字 → 贴纸 → 音效 → 震屏 → 定格 → 片尾卡
- [ ] 音频处理：音效出现时压低 BGM，整体响度归一化
- [ ] 渲染服务：从队列取任务，支持 540p 预览和 1080p 成片两种输出
- [ ] 用 Remotion Studio 对着阶段 2 的真实脚本逐个调效果，和阶段 0 的手工切片对比

### 3.2 后端与编排（第 8–9 周）

- [ ] `backend/` 初始化 Spring Boot 3 + MyBatis-Plus + MySQL + Redis，用 Flyway 管理建表脚本
- [ ] 按技术方案里的数据模型建表，先建主链路用到的：streamer、stream\_session、candidate、clip、clip\_script、clip\_variant、render\_output、review\_log、job
- [ ] 开播检测与录制管理：轮询直播状态，创建场次，下播后触发任务链
- [ ] 任务编排：Redis Stream 分发任务，Python / Node Worker 消费后回调 `/internal/jobs/{id}/result`；失败重试 3 次、幂等
- [ ] GPU 启停：队列里有 GPU 任务时调云厂商 API 开机，空闲 10 分钟关机；若用方案 D，实现 AutoDL 优先、阿里云兜底
- [ ] 把 `worker/` 脚本包成队列消费者，和 `renderer/` 各自打成 Docker 镜像

### 3.3 审核后台（第 9–10 周）

- [ ] `admin/` 用 Vue 3 或 React + 组件库搭建
- [ ] 页面：场次列表 → 切片列表 → 切片详情（多版本预览、脚本时间轴、逐项开关特效、改花字、拖起止点、选标题封面、通过 / 拒绝）
- [ ] 修改后保存为新版本脚本并重新渲染；记录审核耗时和修改差异
- [ ] 主播配置页：画面布局框选、风格包、词库、信号权重

进度（2026-11-10）：审核后台新增三项反馈闭环，代码和测试已完成，还没在服务器上跑过真实数据。(1) 审核页一键原因（开头 / 结尾太早太晚、不好笑、要前情才懂、只是念SC、重复的梗、主播不想发、特别好笑），分盲审和快审两种模式，并记录每条审核耗时；只有盲审的标注进评测和权重校准，边界反馈攒够 8 票且一边倒才提示调粗筛前后秒数。(2) AI 初稿另存原稿，和人工终稿对比得到“剪辑口味”，攒够 5 条且来自 2 场以上才写进初稿提示词 edit\_v2。(3) 梗转正并入主播档案（热词、字幕、标签、提示词），禁区话题命中时精排判不切、审核页标红。部署后在记忆页点一次“更新精排记忆”才会看到数据。

**梗库补齐（热门抓取 + 向量检索）**：补上技术方案里梗库两处没做的部分。每天自动抓一次 B站综合热门、每周必看的标题和热搜词（只抓文本，每天 4 个请求；热评未做），提炼高频短语，按近 7 天加权热度衰减；新梗默认待确认，后台“梗库”页填含义和尺度启用，命中黑名单词 / 禁区话题直接拉黑。生成 AI 剪辑初稿时用精排结论当情境，百炼文本向量在已启用的梗里检索，没有 Key 时退回字面匹配；提示词升级为 edit\_v3，一条最多 2 个梗、间隔 15 秒，模型编的梗会被去掉；编辑器里能看到用到的梗和理由，统计每个梗被用几次、人工终稿保留几次，保留率低的降权。Python 测试 72 个通过，监控脚本测试 12 个通过。

**剪辑初稿多版本**：AI 评分靠前的前 5 个候选，每条按「克制 / 标准 / 热闹」三个风格档位各生成一版初稿（提示词 edit\_v4；点“AI 初稿”时先选版本，默认三个都选、可以只选其中几个，人勾选的不受排名限制；批量生成时只对前 5 个出多版本，其余只出标准版），三版共用同一份梗库检索结果，各自受密度约束和梗数量限制。成片编辑器顶部可以切换版本、立即预览；选中的那一版成为当前脚本和 AI 原稿（剪辑口味按它对比人工修改），选了哪一版会记录下来。技术方案页「剪辑脚本」那一行已提交修改建议。Python 新增 3 个测试，后端切换逻辑用小程序验证。

进度（2026-11-10 晚）：新增“边播边筛”和“主播周报”，代码和测试已完成，还没在服务器上跑过真实直播。(1) 边播边筛：`.env` 里 `KIYA_LIVE_SCREEN=1`（默认关）后，直播中每 30 分钟对已录完的分段粗筛一次，只出候选、不转写不精排不剪切（低优先级，避免和录制抢 2 核 CPU）；审核页顶部有“临时结果”横幅；各分段特征单独缓存，下播后的正式粗筛只补最后一段；正式结果覆盖临时结果后，已标的 Y/N 按片段起点 5 秒内对应过去，对不上的才丢。(2) 主播周报：后台新页面，本周最火的梗 TOP5（含较上周涨跌）、高光场面、哪类内容更出效果（高光攒够 5 个才出占比）、观众弹幕词云；一键导出单个 HTML 文档，只含适合主播看的内容，不含审核备注、通过率、禁区话题；需要先对本周场次做过转写和精排。

### 3.4 上云（第 10 周）

- [ ] 按选定方案购买常驻服务器和 OSS，配置 14 天生命周期规则
- [ ] 用 docker-compose 部署 backend、MySQL、Redis、录制、粗筛 Worker；制作 GPU 实例的自定义镜像（预装模型权重）
- [ ] 把本地录制切换到云上，新旧并行运行一周再停掉本地
- [ ] 端到端跑 3 场真实直播，记录每场从下播到出片的时长和费用

**交付物**：云上可无人值守运行的完整系统；审核后台；部署文档。

**验收**：连续 3 场下播后 1 小时内自动出片；审核通过率 ≥ 60%；单条处理 ≤ 5 分钟；单场费用与估算偏差不超过 30%。

**常见坑**：Remotion 渲染吃 CPU 和内存，并发数要限制；GPU 实例冷启动时间要单独计时优化；Worker 回调接口要做内网鉴权。

## 阶段 4：创意增强与数据闭环（第 11–13 周）

**目标**：把“有活儿”的能力加上去，并让发布数据反哺算法。每项功能上线后用版本胜率和完播率验证，没效果就关掉。

## 贯穿全程的工程规范

一个人业余开发，最怕的是隔一周回来忘了做到哪、改动后不知道效果变好还是变坏。下面这些从阶段 1 开始就做。

| 方面 | 做法 |
| --- | --- |
| 仓库 | 单仓库 `kiya-clipper`，目录 `backend/ worker/ renderer/ admin/ deploy/ eval/ schema/ prompts/`；一个功能一个分支，合并前自己过一遍 diff |
| 配置与密钥 | API Key、云账号放 `.env`，不进 Git；主播配置和权重用 YAML 进 Git |
| 共享契约 | 剪辑脚本和任务消息的 JSON Schema 放 `schema/`，Python、TypeScript、Java 从同一份生成或校验 |
| 实验记录 | 每次改权重、提示词、模型，都跑评测并记入 `eval/results.csv`：日期、版本、命中率、费用 |
| 测试 | 信号计算、脚本校验器、任务状态机写单元测试；用一段 5 分钟的固定样例录像跑端到端测试 |
| 日志 | 每个 job 带 session\_id 和 clip\_id 输出结构化日志，大模型请求记录 token 数和费用 |
| 告警 | 开播没录上、弹幕连接断开、job 失败 3 次、GPU 实例开机超时、磁盘使用超 80%，推送到手机（企业微信 / 钉钉 / Server酱） |
| 费用控制 | 云账号设月度预算告警；GPU 实例设最长运行时间，超时强制关机，防止忘关机 |
| 部署 | docker-compose 一键部署；用 GitHub Actions 在推送后自动构建镜像；数据库变更只通过 Flyway |
| 备份 | MySQL 每日备份到 OSS；评测集、梗百科、提示词都在 Git 里，不会丢 |

## 每周节奏与上线前检查清单

**每周节奏**（按业余每周约 10–15 小时）：

1. **周初 30 分钟**：看上周的评测结果和告警，定本周要完成的 3–5 个任务。
2. **工作日晚上**：做功能，每天结束前提交代码并在任务里写一句进度。
3. **周末**：跑一遍评测集；审核并发布本周切片；补充梗百科和评测标注。
4. **每个阶段末**：对照验收门槛自查，没过就加一周优化，而不是硬进入下一阶段。

**上线前检查清单**（阶段 3 末切换到云上自动运行前）：

- [ ] 书面授权已到位，授权范围覆盖当前用到的素材和手法
- [ ] 字体、音效、BGM 全部确认可商用，`asset.license` 已填
- [ ] 录制断线重连、下播触发、任务重试都用真实场次验证过
- [ ] 告警能推送到手机，已故意制造一次失败验证
- [ ] GPU 实例空闲自动关机和最长运行时间都生效，云账号预算告警已开
- [ ] OSS 生命周期规则生效，MySQL 每日备份可恢复
- [ ] 审核后台只有自己能访问（登录鉴权 + HTTPS）
- [ ] 切片号简介、投稿类型（转载并注明来源）、非官方声明已就绪
- [ ] 主播知道如何提出“这条不要发”，有快速下架的流程

## 多主播支持（2026-11-10）

进度：把「主播」从全局硬编码抽象成可配置实体，代码和测试已完成，还没在服务器上跑过真实数据。

- **主播标识**：`KIYA_STREAMER`（默认 `kiya`），贯穿配置、数据、环境变量、数据库。首位主播 kiya 完全兼容，无需迁移。
- **配置**：新主播复制 `config/streamers/_template.yaml` 为 `config/streamers/<主播标识>.yaml`；`kiya` 继续用 `config/kiya.yaml`（回退路径）。
- **数据隔离**：场次目录从 `output/<场次>/` 变为 `output/<主播标识>/<场次>/`，`_memory` / `_llm_cache` 靠 `sess.parent` 自动按主播隔离；评测在 `eval/<主播标识>/`。旧的 `output/<场次>/`（无主播层级）按默认主播处理，不用搬。
- **worker**：入口脚本（screen / analyze_danmaku / transcribe）加 `--streamer` + 输出目录分层；下游 14 个脚本配置解析统一走 `clipper/streamer.py` 的 `resolve_config`；rerank / autoedit 显式传 `cache_dir=sess.parent/_llm_cache`。
- **backend**：`schema.sql` 的 `live_session` / `candidate` 加 `streamer_id`（默认 `kiya`），唯一约束改组合；`WorkerPaths` 的 output / eval / reviews 按主播分层；`SessionService` 所有查询按 `streamer_id` 过滤。
- **监控**：`kiya_monitor.py` 从主播配置读 `room_id` / `name`（正则提取，不引入 PyYAML），`KIYA_ROOM_ID` 仍可覆盖。
- **测试**：`worker/tests/test_streamer.py` 6 个测试通过。monitor 测试需在 Linux 跑（Windows 下 GBK 编码 + `.venv/bin/python` 路径不兼容）。

设计和使用见 [多主播支持.md](多主播支持.md)。已知边界：主播间对比分析还没做（依赖多个主播都攒够数据）；字幕样式表和贴图库仍是全局共享的。
