# kiya 切片流程升级实施任务书

本文可直接交给负责实现的三方模型。任务是在现有仓库中分批完成切片流程升级，每批交付代码、可复现的验收结果和后续入口。遇到与实际版本不同的实现，先核对代码和已落盘数据，再按本文要达到的行为接续。

## 一、任务目标

把连续音画精排得到的原片依据用于选段、编排、预览质检和审核反馈。最终要能回答下面四个问题。

1. 为什么这段值得剪，系统还有没有漏掉同类片段。
2. 为什么建议从这里开始、在这里结束。是否有另一个有实际取舍的方案。
3. 哪些原声、关键画面和阅读时间必须保留。它们在成片中对应哪里。
4. 人工为什么改了边界或效果，这一类错误在后续新场次是否减少。

本轮以 kiya 流程为对象。沿用已有粗筛、分窗音画分析、模型配置、剪辑器和渲染器。模型继续从当前素材判断，蒸馏规则只提供判断条件。参考作品的台词、人物、标题、镜头和特效素材留在研究记录。

## 三、跨阶段的数据和时间约定

### 3.1 时间坐标

| 坐标 | 用途 |
| --- | --- |
| 整场原片秒数 | 候选、事件、必保证据、缺口和审核定位。多段录播先按文件偏移映射到整场坐标。 |
| 素材窗口局部秒数 | 当前编辑的 `trim`、`cuts`、效果及相应编辑入口。使用已有 `window.start` 转换。 |
| 成片局部秒数 | 渲染后的字幕、画面和声音复核。通过实际保留区间映射，跨删除接缝时可映射为多段。 |
| 原片帧 PTS | 需要逐帧核对的画面边界。注明来源文件、原片帧坐标与对应整场时间。 |

区间统一按左闭右开处理。现有代码对时长、数值精度和渲染帧存在约束，优先复用这些校验。显示可以四舍五入，覆盖检查用运算所需精度。遇到跨文件缺素材时保留间隙，后段映射仍使用原场时间。选中区间落在缺口时明确标为待复核。

截图请求时间、模型估计区间、ASR 词句时间和原片解码帧时间分别保存。模型描述与某个邻近 PTS 的对应关系只登记为复核线索。精确声尾、说话人归属和字幕首帧在核对到相应证据后再提高证据等级。

### 3.2 必保项和关联标识

沿用候选的场次、原序号和事件 ID。当前 `AVxxx` 只能在它所属的精排结果内引用。需要跨草稿、质检或审核记录追踪时，和候选标识、精排版本或证据修订号一起存。重新粗筛、换源素材或重新精排后校验关联，保留旧草稿引用的旧证据，避免旧 ID 被解释成新观察。

以下是交接含义示例。字段命名可以复用已有结构，落盘时确保上下游使用同一个定义。

```json
{
  "candidate": {"session": "example-session", "rank": 2},
  "event_id": "example-event",
  "evidence_revision": "example-rerank-revision",
  "required_evidence": [
    {
      "id": "AV007",
      "start": 94.12,
      "end": 96.48,
      "modality": "audio",
      "role": "effective_response",
      "basis": "model_observation",
      "reason": "保留改变观众理解的最终答复"
    },
    {
      "id": "AV008",
      "start": 95.30,
      "end": 97.14,
      "modality": "visual",
      "role": "result_readability",
      "basis": "source_frame_review",
      "reason": "保留结果画面及原有文字阅读时间"
    }
  ]
}
```

在生成阶段把 `video_evidence.must_keep_ids` 解析成可校验的区间和来源。旧结果只有 `required_reaction` 时，继续支持它。未提供新字段的旧场次继续按旧规则运行，质检中把缺失的新检查记为不可评估。未知 ID、失效来源、超出可用素材、音画缺口和确认缺失分开记录。

## 四、第一批｜必保证据贯穿精排、初稿、剪切、渲染与质检

第一批直接解决已经判定值得保留的信息在后续步骤丢失的问题。先建立共用保护校验，再接 UI 和发布判断。

### 4.1 接通共用保护校验

1. 从精排的有效证据生成必保区间，记录类型、原因和版本。复用已有 `required_reaction` 检查所依赖的区间覆盖思路。
2. 对自动选段、模拟裁剪、手工片中删除及自动营业话删除，调用同一套保留区间与覆盖校验。检查必保区间是否完整连续保留。确有必要支持跨多个保留段时，显式记录需要连续的证据以及可分段的证据。
3. 自动营业话清理与必保区间冲突时保留冲突内容，并把原因写入计划。人工删除产生同样冲突时，保留人工操作和实际计划，显示缺失的证据及对应原片时间。
4. 核对 `cut.py` 的独立剪切入口、编辑器试渲染、完整渲染三条路径。入口共享同一套已应用删除区间。编辑器预计时长、渲染器实际裁剪和质检应能互相核对。
5. AI 初稿应用主备剪法后，自动确保素材窗口内的必保内容完整落进 `trim`。必保内容超出当前素材窗口时，标明需要扩窗的整场区间。出现明确的新触发时，边界校验同时提示可能的跨事件混入。

### 4.2 让渲染质检核对实际结果

- 在渲染计划中保留真实采用的区间及原片到成片的映射。质检读取本次渲染使用的脚本修订和计划，能定位到具体成片、素材和分辨率。
- 声音方面先校验必保原声区间被连续映射。遇到音轨缺失、已知静音处理或所需时间不在成片内时，提示具体区间。仅能从时间证明保留时，记录时间层面的结论。
- 画面方面检查关键信息出现时的裁剪、放大和叠加效果。只有在位置、尺寸和区间均可核实时才判定遮挡。坐标或跟踪信息不足时提供回看时间并标待复核。
- 字幕和结果页分别检查。人工校对字幕用最终渲染事件核验阅读时间。原画面自带字幕或结果页直接核对画面的可用时长和遮挡，避免把转写字幕当作替代证据。
- 质检结果包含证据 ID、原片区间、成片区间、原因和建议复核动作。可沿用现有错误和警告展示。
- 审核预览允许在有提示时生成，已有显式的必保失败行为按实际入口保持兼容。最终推荐或正式发布前，已确认的必保损失应拦在当前发布闸门。效果遮挡疑点、读速偏快和声尾未确认走人工复核。覆盖确认要绑定当前成片，重新渲染后重新核验。

### 4.3 这一批的最低验收

- 选择了正确边界，但营业话自动删除试图移除完整回应。审核剪切与最终渲染仍保留该回应。
- 同一回应被用户从中间手工删掉。审核预览指明原片和成片位置，成片质检能检出，推荐发布保持待复核。
- 一条片跨录播文件，来源有时间缺口。结果继续保留缺口，两个文件的时间不会被提前拼平。
- 一条字幕跨删除接缝，质检使用最终事件和实际成片坐标。
- 使用一个已有剪辑 JSON、一个仅有 `required_reaction` 的剪辑 JSON 和一个新版有必保项的剪辑 JSON，分别验证读取和渲染。

## 五、第二批｜叙事判断、剪点对照和 AI 草稿采用

### 5.1 精排补充叙事任务

保持现有连续音画取证和精排输出字段。在事件判断中补充本条的主角、叙事目标、看点、有效回应与风险依据。把可用性与内容潜力分开，候选有价值但缺必要前情时，保留它的潜力和待补项。

区分原片发生的动作、当事人口述、弹幕建议、创作者演绎和已确认结果。标题、封面文字和剪辑效果都以成片里可支持的表述为准。主播语气、玩笑对象和参与者归属存疑时，记录哪一句或哪一帧需要回看。

### 5.2 让主备剪点确实有区别

- 复用 `boundary_options`。先提供一个可用主方案。存在不同取舍时再给一个备选。
- 每个方案记录整场起止、保留的必要前情、必保证据、剪早的损失、剪晚的新增内容和风险。
- 主备方案都调用第一批的覆盖校验。短版如果丢失会改变事实理解的结论，可以作为问题对照展示，状态标明待复核。
- 把结果回答、反应声尾、字幕读完和新话题开始分开标注。AI 推断的几秒范围与已复核的帧时间分别展示。
- 合并或隐藏同边界与近似操作的方案。备选出现的理由应是不同的叙事取舍。效果强度另走已有克制、标准、热闹档。
- 只有画面和声音配合确实有剪辑价值时再提示音画分开处理。先核对现有渲染器对音画不同步剪切的支持。流程未支持的手法以人工建议给出。

在扫码案例里，短版在「一般都是用后置吗」后收尾。完整版继续保留主播确认或反应。对照说明两版分别能证明「有人提建议」「主播理解了建议」或「实际换了镜头」。只有原片出现对应证据时才能采用最后一种表述。

### 5.3 把 AI 初稿从直接覆盖改为先生成、后采用

1. 保留「AI 初稿」入口。任务成功后写入独立草稿，关联场次、候选序号、开始时的编辑修订、边界方案、风格档、使用的 Prompt 与证据修订。
2. 编辑器可比较当前编辑和新草稿的原片边界、片中删除、字幕修改、特效增删和必保项。差异大的位置可局部预览。
3. 保持现有多风格草稿选择方式，并显式区分剪法方案与风格档。局部预览的文件名或缓存键包含草稿 ID、相关参数和分辨率，避免与当前成片混淆。
4. 「采用」走已有修订检查和历史归档。生成期间用户又保存了内容时，提示版本已变化，提供重新比较的入口。采用前将最新手工改动保存为可恢复版本或草稿。
5. `AUTO_EDIT` 现有任务参数和旧调用方应能继续工作。若保留明确请求覆盖的 CLI 方式，对应入口要有清晰含义。后台常规 AI 初稿使用待采用草稿。
6. 采用后的草稿作为这次人工稿的 AI 对照基线。重复生成新草稿继续给旧稿留存对应基线。

验收至少覆盖生成失败、重复点生成、两个草稿先后完成、生成过程中发生人工保存、查看草稿后取消、采用并恢复上一版、旧场次只有单份 `.ai.json`。正式脚本只在明确采用或原有授权的写入路径中变化。

## 六、第三批｜低热度语义召回和事件去重

### 6.1 先测粗筛基线

在修改召回前，选 3–5 场互相独立的 kiya 录播。每场挑若干低热度区间，并保留少量正常高热度区间作对照。审核者先根据原片标值得剪的事件，记录对象、触发、主看点、有效回应和可接受的区间。随后再看现有热度候选和探索队列。只使用时间交叠会错把相邻两件事当成召回成功，验收时须核对触发和回应归属。

用已定区间做固定对照，记录人工参考事件数、热度路找回数、探索路额外找回数、冗余候选和需要审核的候选数。单场数据量小时一并记录分子和分母。

### 6.2 扩展现有探索队列

- 入口沿用 `recall.py` 和 `exploration_candidates.json`。用现有转写、SC、音量或画面变化建立提名。价值判定来自实际事件而不是触发词本身。
- 依次覆盖问答闭环、迟到的反转、安静的情绪表达、主播有辨识度的反应和画面承担信息的内容。视频缺失时保留文本候选及证据限制。
- 每条候选记录来源、触发、对象、提名原因、可用窗口和待验证项。保留已有手工标记优先级、来源回溯及探索的候选预算。
- 同一事件多路命中时合并来源。对象、触发或回应有差异时分别留候选。仅共享场景、相似用词或存在重叠时，使用待复核状态。
- 精排分窗发现一个独立事件时，可生成拆分候选并记录父事件。限制重复派生，下一次重跑仍能关联同一个候选。探索结果在审核队列比较，确认有效后再纳入日常排序。

验收时在相同场次、相同人工标签上对比热度路与联合召回。报告新增找回和每条新增所带来的审核工作量。低热度弱信号可以增加有效发现，同时也可能引入更多误报，按事件类型展示结果。

## 七、第四批｜审核反馈、维度验收和迭代闭环

### 7.1 收集实际修改理由

先扩展已有 `editdiff.py` 和保存记录。在人工保存时提供轻量的可选原因。默认保留系统能计算的差异，审核者只补模型无法推断的意图。

| 原因 | 应对应的记录 |
| --- | --- |
| 前情太长或不足 | 修改前后起点、补回或删掉的线索 |
| 有效回应被截断 | 必保原声或结果页、修改后的终点 |
| 误串互动 | 新触发或新话题时间、两个事件的证据 |
| 字幕读不完 | 出现与结束的时间、是否为原画面字幕 |
| 画面被遮挡 | 特效类型、被遮挡信息、对应成片秒数 |
| 语气或人物归属误读 | 原话、互动对象、人工修订和待复核点 |
| 主观节奏取舍 | 目标观众、所选剪法、是否保留另一种可用方案 |

每条反馈关联候选、所采用的 AI 草稿、证据修订、模型与 Prompt 版本、原片边界、保存后的编辑修订。可选标签和值从保存接口做一致性校验。合并同一次修改的重复事件，后续根据具体失败案例更新规则，保留可回滚的 Prompt 版本。

### 7.2 五个视角的验收

| 视角 | 要回答的问题 |
| --- | --- |
| 剪辑师 | 候选起止能否定位，必要声尾和阅读时间是否保住，删段接缝是否自然。 |
| 导演 | 观众能否说出主角、事件变化和看点，效果是否服务叙事。 |
| 编辑 | 标题、封面文字和成片是否支持同一个事实，可发布性判断是否解释风险。 |
| 首次观看的观众 | 能否复述谁回应什么、发生了什么、最后结果怎样，最早看懂和开始觉得拖的位置在哪里。 |
| 主播 | 有没有误认说话人、改变玩笑对象、割裂语气或遗漏让互动能被正确理解的回应。 |

观众对照给同源版本随机顺序，先记录复述和时间，再问主观偏好。可以从 3–5 场独立录播做首轮。没有实际观看反馈时，把该项标为待收集。模型回看可以单独用于技术复核和筛选样本。

### 7.3 报告质量与成本

每轮记录已标注事件、召回与漏选、独立候选数、必保损失、误串事件、语境误读和疑似遮挡。分别统计粗筛未召回、精排判断错误、初稿改坏、剪切丢失、渲染遮挡和审核拦截。报告实际模型请求数、失败与无用量记录、缓存命中、tokens、额外审核量和耗时。

对照中固定素材、模型、转写和主要配置。每批只比较所改动的阶段。圈定能改进下一轮 Prompt 或流程的案例，保存对应原片、版本和验收意见。

本轮报告使用统一口径。召回率以找回的不同人工事件数除以标注事件总数。误串率以被误合并的候选数除以已核对事件归属的候选数。必保损失以缺失证据的成片数除以具有可核验必保项的成片数，同时列出缺失的证据 ID。审核量报告需要新增查看的候选数及耗时。证据不足单列，保留各指标的分子、分母和排除原因。

## 八、兼容、故障恢复和发布闸门

- 老场次缺新证据、缺事件字段、只有一个剪点或只有一份历史初稿时，仍可打开、编辑和渲染。旧配置继续按已有执行入口解析。
- 首次运行或重跑时，区分粗筛版本、源素材修订、Prompt 版本和证据修订。源文件变更、候选重排或渲染设置变更时检查对应缓存与草稿引用。
- 窗口失败后保留已成功观察和失败原因。重跑复用已有结果。限流或服务拒绝时保留缺口，用已有素材继续处理独立可完成的部分。
- 审核页显示推荐、备选和待复核。发生具体证据损失的成片在发布前由实际发布入口检查。预览和研究输出与正式成片要能区分，记录使用的文件和对应修订。
- 新增音画请求沿用现有模型连接和用量记录。批量验证先跑小样并估算放大后的请求与时长，按当前明确授权的预算执行。失败和用量未知的请求保留账目。
- 功能按主播或现有开关配置逐步启用。回滚提供选用旧 Prompt、关闭新增召回或恢复上一版编辑脚本的路径。保留已生成的研究结果供对照。

## 九、测试和交付顺序

### 9.1 可直接用于验收的用例

| 场景 | 应看到的行为 |
| --- | --- |
| 候选笑点后隔一窗才出现回复 | 前后文续查，相关回应进入证据。另起话题有独立边界。 |
| 跨录播文件且中间缺素材 | 音画覆盖有缺口，证据保留整场时间，相关候选可预览及待复核。 |
| 一闪而过的结果字幕 | 有可回看的片段或帧锚点，建议保留可读时间，精度等级可追溯。 |
| 同一句被自动营业话和手工删除命中 | 自动处理保护必保项，手工删除触发具体提示。 |
| 精排选对但初稿裁短 | 初稿将窗口内必保项补进裁剪，窗口外证据显示需要扩窗。 |
| 放大挡住易读结果 | 质检能定位时显示冲突，缺画面坐标时给回看片段。 |
| 同场相邻像同一互动 | 对象或触发不同则分别留候选，真正重复则合并来源。 |
| 跨场次的低热度温柔回应 | 指标可见新增召回及其带来的审核量。 |
| 初稿生成期间人工编辑 | 生成稿单独生成，采用时按修订检查，旧内容可恢复。 |
| 模型失败或部分窗口缺证 | 已成功窗口继续可读，失败状态、未知用量和缺口全部可追溯。 |

### 9.2 每批怎么交付

1. 先完成第一批的端到端必保校验与回看定位。可同时用现有探索队列采集召回基线。
2. 再完成第二批的边界方案对照和草稿采用。这批依赖第一批覆盖校验。
3. 基线显示低热度事件有稳定漏选时，完成第三批的召回改进及对照。按场次记录正反例与误报。
4. 补齐第四批反馈字段与新场次复测。把前几批发现的问题转成可回看的回归案例。

每批从现有入口回归，兼顾 CLI、后台任务和审核编辑器。运行相关 Python 测试、后端测试和前端构建。后端按仓库声明使用 JDK 17。本地当前连续音画相关验证已包含合成视频的百炼请求，工程端到端验收仍需要真实 kiya 场次。旧测试如果失败，核对变更前能否复现并在交付中区分。
