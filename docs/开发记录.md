## 2026-11-12｜项目阶段总结与后续方向

> 来源：用户提供的昨日总结截图。本文将其中内容作为项目背景、约束和待决策事项保存；“我建议的顺序”属于建议，执行前仍以用户最新确认的安排为准。

### 已确定事项

- 11 月 13 日结束前不继续开发，先讨论和汇总。
- 总目标：在尽量不人工修改的情况下，成片评分达到 6 分或以上；评分口径还需要校准，终态以基本不碰片为目标。
- 第一阶段目标：全自动出待发布成片，但不自动发布，由人工审核后发布；审核打分和原因作为主要校准信号。
- 学习方向是“编排手册”，不是训练模型权重；账号从冷启动开始，以审核打分为主，平台数据暂不纳入学习。
- 架构方向是 agent 加工作流；判断环节使用 agent，硬规则由程序校验，优先质检回路。
- 多模型通过模型档案配置和任务分配支持，允许运行时切换中转 API。
- 成本暂不作为主要限制；单场成本重点受服务器 2C2G 的渲染耗时和磁盘影响。

### 已知问题

- 当前成片效果存在选片、边界、编排和字幕四类问题，样例还没有系统收集。
- 营业话（欢迎、谢礼等）会混进切片。
- 呼应检索噪音较大，现有评分尚未在真实数据上充分验证。
- Remotion 渲染、Java 编译、Vue 构建、真实上传和大模型调用判定还没有完整真实环境验证。
- 工程方面存在大量未提交改动、测试覆盖有限、临时文件未清理、数据目录布局不统一等问题。

### 待定事项

- 营业话的识别范围，以及营业话落在片段中间时的处理方式。
- 5–10 条成片的评分和一句话理由，作为首批校准样本。
- 过渡期长度、达标线，以及什么条件下从人工审核切换到自动发布。
- 数据目录布局以哪一种方案为准。
- 中转接口是否需要保持 OpenAI API 兼容。

### 建议推进顺序

以下是总结中的建议顺序，不视为已批准的执行计划：

1. 在真实环境把已有代码完整验证一遍，并按功能拆分提交，后续工作建立在可复现基线上。
2. 固化评分表和校准样本，先建立可比较的衡量方式。
3. 过滤营业话，优先处理边界裁剪和其他硬伤。
4. 做质检回路。
5. 回收特征加指标快照数据。
6. 做多模型配置，并用评测集对比。
7. 复盘 agent，最后再把选片和剪辑收敛成 agent。

### 验证结果

- 已将截图内容按“已定 / 已知问题 / 待定 / 建议”分类记录。
- 本条记录不改变运行时代码，也不代表待定事项已经作出技术决策。

### 风险与待办

- 后续开发前应先确认当前基线、提交边界、数据目录规范和评分表，避免在未验证的代码上继续叠加功能。
- 评分标准和校准样本一旦确定，应同步记录到评测目录，并在后续功能记录中引用。

## 2026-11-13｜营业话过滤与中间片段删除

### 背景与目标

- 按阶段总结中的第 3 项，先处理成片质量中的营业话问题。
- 片段中间的纯欢迎、谢礼和念弹幕内容也应尽可能去掉，同时保留有实际内容的感谢或互动句。

### 改动内容

- 新增 `worker/clipper/boiler.py`：用保守规则识别纯营业话，生成删除时间段，并提供保留区间和压缩时间轴计算。
- `worker/clipper/boundary.py`：精排边界结果增加 `removed` 字段和处理说明。
- `worker/scripts/cut.py`：没有精排结果时也从转写中检测营业话；按保留区间重新拼接视频；字幕和逐字时间同步压缩；在 `clips/windows.json` 保存删除明细和实际输出时长。
- 修正 `--no-subs` 行为：关闭字幕只影响字幕输出，仍然读取转写并执行营业话过滤。
- `worker/scripts/render.py`：最终 Remotion 源视频沿用同一套删除规则，并同步压缩字幕、花字和贴图时间。
- `backend/.../SessionService.java` 与 `admin/src/views/Review.vue`：返回并展示删除区间，审核页跳转原话时自动映射到压缩后的视频时间轴，被删除句显示为“已移除”。
- `worker/tests/test_phase2.py`：增加营业话识别、内部删除区间和时间轴压缩的回归断言。

### 验证结果

- `python -m py_compile` 已通过：营业话分类、边界、剪片和渲染入口均可导入。
- 管理端 `npm run build` 已通过。
- 直接规则验证通过：欢迎语和谢礼被识别，有内容的“谢谢你提醒我这个问题”被保留，中间删除后的保留区间和时间映射符合预期。
- 用 12 秒合成视频实测：删除 2 段各 2 秒营业话后，输出视频为 8 秒，`windows.json` 正确记录 2 个删除区间和 `output_duration=8.0`。
- Admin `npm run build` 已通过；Backend 使用 JDK 17 执行 `mvn -q -DskipTests compile` 已通过。
- 完整 pytest 尚未执行：当前环境没有安装 `pytest`。
- 之前使用默认 JDK 8 的编译失败属于环境版本问题，切换到仓库现有 JDK 17 后已通过。
- Renderer 没有 `build` npm script，暂未执行独立构建。

### 风险与待办

- 规则目前只覆盖明显的欢迎、谢礼和念弹幕句，真实 ASR 文本需要继续收集误判和漏判样例。

- 需要在一场真实转写场次上执行 `cut.py` 和 `render.py`，检查音画拼接、字幕、花字和审核跳转是否都对齐。
- 如果真实样例中营业话与内容句经常混在同一句，需要增加句内切分规则或交给精排模型标注后再剪。

## 2026-11-13｜建立质检回路

### 背景与目标

- 按阶段总结的第 4 项，把程序硬检查、人工审核反馈和 AI 初稿/人工终稿差异串成可追溯回路。
- 先生成报告并展示问题，不改变现有渲染成功语义；发布门槛后续再根据真实样本校准。

### 改动内容

- 新增 `worker/clipper/quality.py` 和 `worker/scripts/quality_check.py`。
- 程序检查成片文件完整性、视频/音频流、实际时长、黑帧、音画时长差、字幕事件时间、营业话残留、效果密度和贴图素材。
- `render.py` 成片落盘后自动写 `output/<场次>/quality/<序号>.json`；CLI 支持单条和全场检查，全场额外汇总 `edit_taste`。
- 质检报告在存在 AI 初稿和人工终稿时写入 `edit_diff`，保存删除、新增、改字、移动效果和裁剪偏移。
- 审核记录增加 1–10 的人工评分，保存到 `review_meta.json`，同步导出/导入 `eval/reviews/<场次>.csv`，审核页可以录入、清除和查看评分。
- 审核列表和详情显示质检通过、警告或失败状态。
- `worker/README.md` 增加质检命令、报告位置和字段说明。

### 验证结果

- `python -m py_compile worker/clipper/quality.py worker/scripts/quality_check.py worker/scripts/render.py` 通过。
- `git diff --check` 通过。
- 管理端 `npm run build` 通过。
- 后端使用 `C:\Users\84741\.jdks\jbr-21.0.11` 执行 `mvn -q -DskipTests compile` 通过；默认 JDK 8 会因项目现有 record / switch 语法报错，不能作为本次代码结论。
- 当前环境未安装 `pytest`，未执行 Python 测试集；真实成片的 ffmpeg 黑帧和音画检查仍需在有素材的场次上跑一轮。

### 风险与待办

- 黑帧检查依赖 ffmpeg，阈值目前是 0.15 秒检测、0.5 秒报告、1.5 秒边缘黑帧报错，转场素材可能需要按样本调整。

## 2026-11-13｜主题化抽象封面与多方案选择

### 背景与目标

- 旧封面只有截图、底部暗色遮罩和通用大字，无法表达片段的反差、破防、口胡或翻车主题。
- 目标是让封面先表达一个视觉笑点，再用短文案辅助，而不是把完整标题直接压在截图上。

### 改动内容

- `worker/clipper/publish.py` 新增主题概念推导和主题化封面渲染：反差、情绪超载、语言事故、操作失误、当场社死、抽象事件六类主题。
- 每次生成三种构图：人物海报、漫画冲击、抽象事件卡；使用不同色板、符号、斜线、色块和信息层级。
- `publish_pack.py` 自动生成三张候选封面，并保留 `cover_concept`、`cover_variants`、`cover_variant` 元数据；可用 `--cover-variant` 和 `--cover-theme` 重新选择。
- 后端封面接口支持构图和主题参数，并支持通过 `?variant=` 预览不同方案。
- 编辑器发布卡片显示三张候选封面，点击候选即可重新生成并设为主封面。

### 验证结果

- 主题封面图片级冒烟检查通过：三种构图均输出 1920×1200 JPEG。
- Python 编译和 `git diff --check` 通过。
- JDK 21 下 Maven 编译通过；Admin `npm run build` 通过。
- Windows 环境无 `fc-match`，图片冒烟使用系统字体文件替代；Linux 服务器继续使用配置中的 `fc-match` 字体名。

### 风险与待办

- 当前抽象元素由程序化图形生成，还没有接入透明人物抠像和专门的主题插画素材；真实直播画面上的主体识别效果需要用样片复核。
- 三张方案目前默认全部生成，服务器渲染发布包的耗时和磁盘占用会增加；后续可根据人工选择数据减少低命中构图。
- 需要收集不同主题的人工选择和发布点击表现，再校准主题判断、短文案和色板。

## 2026-11-13｜增加 Seedream 生图封面方式

### 背景与目标

- 在程序化主题封面之外增加真正的图像生成方式，利用参考帧和片段主题生成更夸张的抽象视觉。
- 生图方式必须可选、可追溯、失败可回退，不能影响现有发布包和程序化封面。

### 改动内容

- 新增 `worker/clipper/seedream.py`：按火山引擎方舟 Seedream API 调用，支持图片生成、任务轮询、图片下载、data URL 返回和错误归一化。
- `publish_pack.py` 增加 `--cover-mode programmatic|seedream|all`；Seedream 提示词明确要求保留主播特征、不生成文字，中文标题由程序叠加。
- 发布包保存 `cover_seedream_error`、Seedream 文件和 `cover_variants` 元数据；`all` 模式同时保留程序化和 Seedream 候选。
- 后端封面接口支持 `mode`，编辑器发布卡片增加“Seedream 生图”按钮。
- 配置增加 `publish.seedream_model`、`seedream_endpoint`、`seedream_size`，`.env.example` 增加 `SEEDREAM_API_KEY` / `ARK_API_KEY`、`SEEDREAM_MODEL`、`SEEDREAM_ENDPOINT`。

### 验证结果

- Python 编译通过。
- 使用本地模拟参考帧验证 Seedream 适配器代码路径可导入；网络生成未执行，当前环境没有配置生图 Key。
- JDK 21 Maven 编译通过。
- Admin `npm run build` 通过。

### 风险与待办

- Seedream 模型和 API Key 在火山引擎方舟控制台申请，不在阿里百炼控制台；模型名、请求字段和返回结果受账号区域及 API 版本影响，第一次真实调用需要用实际 Key 验证；可通过 `seedream_endpoint` 覆盖地址。
- 修正文档命令示例：Linux Bash 会把 `<场次>` 解释为输入重定向，Seedream 示例改为先设置真实的 `SESSION` 变量再执行。
- 按用户要求将 Seedream 默认模型配置切换为 `seedream-5.5`；如果火山方舟控制台显示的是自定义接入点 ID，应以该 ID 覆盖 `SEEDREAM_MODEL`。
- 根据用户提供的控制台截图确认接入点为 `Doubao-Seedream-5.5 261028`，默认模型 ID 更新为 `doubao-seedream-5-5-261028`。截图同时暴露了 API Key，已提醒用户立即撤销并重新创建，项目不保存该 Key。
- 实际调用 Seedream 5.5 时发现其不支持 `sequential_image_generation` 参数；已从请求体移除，只保留模型、提示词、参考图、尺寸、返回格式和水印字段。
- 参考帧会上传到外部图像服务；正式启用前需要确认账号、素材和主播授权范围。
- 生成费用、耗时和人物一致性需要用 5–10 条真实片段比较，再决定默认是否切换为 `all`。
